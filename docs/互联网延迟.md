# 互联网延迟

本文记录 DouClash 概览页“互联网延迟”面板的语义、数据来源和实现策略。

## 面板目标

“互联网延迟”不是代理测速的别名，而是一个轻量网络诊断入口，用来快速判断当前网络慢在哪里：

1. 本机到路由器/默认网关是否正常。
2. DNS 解析是否可用、是否明显变慢。
3. 访问公网 HTTP 目标是否可达、响应耗时是否正常。
4. 直连策略访问测试目标是否正常。
5. 当前代理链/代理节点访问测试目标是否正常。

因此面板卡片保留公网、路由器、DNS 和当前节点四个摘要指标；点击“诊断”后打开延迟诊断窗口，展示逐项日志。健康检查页面右上角的“网络诊断”是独立的本地 ZIP 报告流程，详见[网络诊断报告](网络诊断.md)。

## Surge Mac 参考

Surge Mac 的 Home 卡片把连通性测试分为三类：

1. **ICMP Ping Test**：用于路由器延迟，反映物理网络或默认网关状态。
2. **DNS Lookup Test**：并发解析固定域名并取最快响应，用于 DNS 延迟，也用于简单确认互联网可达。
3. **HTTP Test**：对目标 HTTP 服务器发送 `HEAD` 请求，计算收到响应头的时间；Home 卡片里的 Internet latency 和 Proxy latency 都属于这类结果。

参考：[Surge Manual - Connectivity Testing](https://manual.nssurge.com/book/understanding-surge/en/)

Surge 的配置还区分两个测试 URL：

1. `internet-test-url`：用于 Internet connectivity testing，同时也是 `DIRECT` 策略的测试 URL。
2. `proxy-test-url`：代理策略的默认测试 URL。
3. `test-timeout`：连通性测试超时时间。

参考：[Surge Manual - Misc Options](https://manual.nssurge.com/others/misc-options.html)。社区配置和实践也普遍把 `internet-test-url` / `proxy-test-url` 配成 `generate_204` 一类轻量 HTTP 目标，例如 [metowolf/Surge.conf](https://github.com/metowolf/Surge/blob/master/Surge.conf)；Sukka 的实践说明 Surge 使用 `HEAD` 请求测试 URL，只要有响应就视为可达，参考：[我有特别的 Surge 配置和使用技巧](https://blog.skk.moe/post/i-have-my-unique-surge-setup/)。

## DouClash 实现

DouClash 采用“摘要卡片 + 诊断窗口”的实现：

1. **摘要卡片：互联网延迟**
   - 对多个公网 URL 发送 HTTP `HEAD` 请求。
   - 默认目标：
     - `https://www.apple.com/library/test/success.html`
     - `https://www.cloudflare.com/cdn-cgi/trace`
     - `https://github.com/`
   - 只统计成功目标，显示平均耗时。
   - 全部失败时显示 `--`。

2. **摘要卡片：路由器**
   - 通过 `route -n get default` 获取默认网关。
   - 对默认网关执行一次 `ping`。
   - 成功时显示 ICMP 往返耗时；失败时显示 `--`。

3. **摘要卡片：DNS**
   - 通过 `dig +time=<timeout> +tries=1 <domain> A` 做一次 DNS 查询。
   - 读取 `Query time` 作为 DNS 延迟。
   - 失败时显示 `--`。

4. **摘要卡片：当前节点**
   - 继续复用 mihomo controller 的节点延迟结果。
   - 优先使用当前选中节点的 runtime delay。
   - 没有有效延迟时显示 `--`。

5. **延迟诊断窗口：逐项日志**
   - 路由器：显示 `Ping <默认网关>: N ms` 或失败原因。
   - DNS：显示 `收到 <域名> 的应答: N ms` 或失败原因。
   - 直连策略：对第一个公网测试 URL 发起 HTTP `HEAD`，显示直连耗时或失败。
   - 代理链：如果 mihomo 内核运行且当前选择不是 `DIRECT`，调用当前选中节点的 `/proxies/{proxy}/delay`，显示“通过 <节点> 连接到 <测试 URL>: N ms”；失败时展示失败信息。
   - 内核未运行、没有节点组或当前为 `DIRECT` 时，代理链条目显示为信息提示，不作为失败。

## 交互策略

1. 面板首次出现时，如果还没有诊断结果，会自动执行一次诊断。
2. 用户点击刷新图标时，后台重新执行完整诊断并更新摘要指标。
3. 用户点击“诊断”按钮时，打开延迟诊断窗口，并重新执行完整诊断。
4. 诊断期间显示加载状态，并禁止重复点击。
5. 诊断完成后写入事件日志，便于排查网络问题。

## 偏好设置

互联网延迟诊断提供这些可配置项：

1. **公网测试 URL**
   - 保存字段：`internetLatencyTestURLs`
   - 支持逗号或换行分隔多个 HTTP/HTTPS URL。
   - 默认值：
     - `https://www.apple.com/library/test/success.html`
     - `https://www.cloudflare.com/cdn-cgi/trace`
     - `https://github.com/`
   - 如果用户输入为空或没有有效 URL，回退默认值。

2. **DNS 测试域名**
   - 保存字段：`internetLatencyDNSDomain`
   - 默认值：`bing.com`
   - 为空时回退默认值。

3. **诊断超时**
   - 保存字段：`internetLatencyTimeoutSeconds`
   - 默认值：3 秒
   - 范围：1 到 10 秒
   - 同时用于 HTTP、DNS 和路由器 ping。

路由器延迟不提供手动目标配置；它始终使用 `route -n get default` 解析出的默认网关。这样可以保持该指标表达“本机到当前网络网关”的语义。

## 取舍

当前不做这些能力：

1. 不保存历史趋势。
2. 不模拟 Surge 的每条规则命中和每个代理链路 hop。
3. 不把 DNS 诊断做成并发查询所有 nameserver。
4. 不单独提供 `proxy-test-url` 偏好；代理链测试暂时复用当前节点组的 `testURL`，没有时使用 mihomo 默认测试 URL。

理由：

1. 当前目标是让“诊断”真正呈现可读的分层结果，而不是只刷新四个数字。
2. 路由器、DNS、直连、代理链四类日志已经能覆盖大多数“为什么慢/为什么不可达”的定位场景。
3. 独立 `proxy-test-url`、历史图表、DNS nameserver 并发诊断可以后续作为增强功能加入。
