# 规则

本文记录 Clash Meow 的规则展示、启停和后续编辑方案。这里的“规则”分两类：一类是 mihomo 运行时通过 controller 暴露的规则列表，另一类是 Profile YAML 里的 `rules` / `rule-providers` 配置原文。

## 添加规则对比

第三方对“添加规则”大致分成两类：

1. **运行时 inspect 型**：KumoApp、MetaCubeXD 更偏向查看和临时操作 `/rules`，不在规则页提供完整的新增规则入口。它们的优点是不会碰 Profile；缺点是不能表达“刷新订阅后仍保留这条本地规则”的长期意图。
2. **Profile override 型**：clash-party 的“编辑规则”会读取 Profile 原文和本地 rule override，把新增规则标记为 `prepend` 或 `append`，删除规则标记为 `delete`，最终写入单独的 override YAML；添加时用结构化表单选择 rule type、payload、proxy，并按规则类型显示 `no-resolve` / `src`。参考：[edit-rules-modal.tsx](https://github.com/mihomo-party-org/clash-party/blob/7ea11bb6452ea05a1d2b2eead0b7f001f05baef4/src/renderer/src/components/profiles/edit-rules-modal.tsx)。

Clash Meow 采用第二类，但不照搬完整规则列表编辑器。原因：

1. Clash Meow 已经把 Profile 原文和 runtime config 分开，新增规则天然应该进入 Profile override，而不是直接写订阅 YAML。
2. 规则页当前仍是运行时视图，不适合一次性承载完整 YAML 编辑器；新增规则先做轻量结构化表单，后续再扩展现有 override 条目管理。
3. 纯文本输入容易写出 `MATCH,,DIRECT`、漏填 proxy 或把 `no-resolve` 用到不支持的类型；结构化表单可以把这些低级错误挡在提交前。
4. 入口使用规则页工具栏的 `+` 图标；承载使用 sheet，而不是独立 window。添加规则是依附当前规则页的短流程，sheet 能避免多窗口焦点漂移和重复打开多个添加窗口。sheet 内的类型、策略候选和实时结果必须在宽度不足时自动折行，展示完整内容；实时结果固定在底部操作区上方，最后用“确定”提交。

## Clash Meow 推荐方案

Clash Meow 分阶段实现规则能力：

1. **规则页是运行时视图**：规则页展示 mihomo controller 当前 `/rules` 的真实结果，用于排障、观察命中和临时启停，不直接代表 Profile 原文。
2. **搜索、筛选与统计优先**：规则列表展示 type、payload、proxy、命中次数、未命中次数、命中率、最近命中 / 未命中和规则集合 size；提供搜索、启用状态、类型、策略和排序能力。
3. **规则开关与新增规则统一持久化到 Profile override**：逐条规则关闭不写 `preferences.json.disabledRules`。关闭规则等价于在当前 Profile 的 `profiles/<id>.rules.yaml` 写入 `delete:`；重新启用规则等价于从 `delete:` 移除。新增规则继续写 `prepend:` / `append:`。
4. **运行态使用最小热更新**：规则开关保存 override 后，当前运行态优先调用 mihomo `PATCH /rules/disable`，避免整份配置 reload；新增规则没有对应的单条追加 API，保存 override 后调用 `PUT /configs?force=true` 热加载 runtime config。两者都不因为规则增删改立刻重启 core；失败时 toast 提示并记录事件。如果 core 未运行，override 和 runtime config 会保留到下次启动时生效。
5. **偏好与规则分离**：规则禁用状态不写入应用偏好；用户对规则的长期修改统一由 Profile override 表达。
6. **规则集合与规则同页管理**：参考 MetaCubeXD，`rule-providers` 放在规则页的“规则集合”tab，展示 provider 名称、behavior、vehicleType、format、ruleCount、updatedAt，并支持更新单个 / 全部 provider。这样排障时不需要在“规则命中”和“规则集合更新”之间来回切页面。

## 持久化策略

Clash Meow 不直接编辑订阅 YAML，原因有三点：

1. 远程订阅刷新会覆盖本地修改，直接改原文容易让用户误以为订阅内容已经被服务端修改。
2. controller `/rules/disable` 使用 runtime index，而 index 会随订阅刷新、rule-providers 更新和配置 reload 改变，不能作为持久主键。
3. 完整规则编辑涉及 prepend / append / delete、`no-resolve`、`src`、rule-provider 与 override 合并顺序，应该在配置层统一设计，而不是塞进运行时 inspect 页。

规则修改采用统一的 Profile override 方案：

1. 用户在规则页关闭某条规则。
2. Clash Meow 用 controller `/rules` 返回的 `type`、`payload`、`proxy` 生成规则字符串，例如 `DOMAIN-SUFFIX,example.com,Proxy`；`MATCH` 这类空 payload 规则生成 `MATCH,DIRECT`。
3. Clash Meow 把该规则字符串写入当前 Profile 的 `profiles/<id>.rules.yaml` 的 `delete:`。
4. 用户重新启用该规则后，从 `delete:` 移除；如果 override 文件已为空，则删除该文件。
5. 新增规则写入同一个 override 文件的 `prepend:` 或 `append:`。
6. 新增规则使用结构化字段生成规则字符串：`type`、`payload`、`proxy` 和附加参数。`MATCH` 不需要 payload；`GEOIP`、`IP-CIDR`、`IP-CIDR6`、`SRC-IP-CIDR`、`RULE-SET` 支持 `no-resolve`；`GEOIP`、`IP-CIDR`、`IP-CIDR6`、`RULE-SET` 支持 `src`。
7. override 文件结构参考 clash-party：
   ```yaml
   prepend:
     - DOMAIN-SUFFIX,example.com,Proxy
   append:
     - DOMAIN-SUFFIX,tail.example.com,DIRECT
   delete:
     - DOMAIN-SUFFIX,old.example.com,DIRECT
   ```
8. `prepend` 规则会插入到最终 runtime `rules` 前面，适合优先命中。
9. `append` 规则会追加到最终 runtime `rules` 后面，适合兜底补充。
10. `delete` 用规则字符串精确删除最终合并后的规则；因此它既能删除 Profile 原文规则，也能关闭通过 `prepend` / `append` 添加的规则。
11. Profile 原文仍保持不变。远程订阅刷新后，override 会继续参与 runtime config 生成，因此用户本地关闭或新增的规则不会因为刷新订阅而丢失。
12. 这个方案的取舍：相比只用 `/rules/disable`，override 不会把长期意图绑定到易变化的 runtime index，也不会把长期意图拆到 `preferences.json`；相比每次都重启或 reload 整份配置，规则开关只用 `/rules/disable` 修改当前运行态，新增规则才 reload runtime config，连接中断更少，更符合 Clash Meow “Profile 是输入，runtime config 是输出”的配置模型。

## 当前实现

当前代码实现运行时规则管理和 Profile 规则 override：

1. 侧边栏“检查”分组提供“规则”tab，显示在“日志”tab 上方。
2. 规则页进入或刷新时从 controller 读取 `/rules` 和 `/providers/rules`。`/rules` 兼容 mihomo 当前实测的数组响应，也兼容 MetaCubeXD 使用的 index 字典响应。
3. 页面提供“规则 / 规则集合”分段切换。规则 tab 显示运行时规则；规则集合 tab 显示 rule providers。
4. 规则 tab 支持搜索 `type`、`payload`、`proxy`，支持“全部 / 已启用 / 已禁用”状态筛选，支持 type 与 proxy facet chips，支持按配置顺序、类型、匹配内容、命中次数和最近命中排序。
5. 每行显示规则类型、匹配内容、命中 / 未命中、size、命中率、最近命中 / 未命中和出站目标；已禁用规则降低透明度。
6. 开关规则时更新当前 Profile 的 `profiles/<id>.rules.yaml`：关闭写入 `delete:`，启用从 `delete:` 移除。
7. 规则 override 更新后通过 `RuntimeConfigBuilder` 重新生成 runtime config。关闭 / 启用规则时，如果 core 正在运行，先调用 `PATCH /rules/disable` 修改当前运行态并刷新 `/rules`；如果该接口失败，再 fallback 到 `PUT /configs?force=true`。新增规则时，如果 core 正在运行，调用 `PUT /configs?force=true` 热加载并刷新 controller 数据。不自动重启 mihomo。热更新返回前保留当前规则列表，不把规则页清空；失败时仍保留旧的运行时数据并提示用户。App 自己写入 runtime config 时会短暂忽略文件监控事件，避免把内部写入误判为外部修改。
8. 规则页工具栏的 `+` 会打开添加规则 sheet；sheet 使用结构化表单生成规则字符串，写入当前 Profile 的 `profiles/<id>.rules.yaml` 的 `prepend:` 或 `append:`，再通过 `RuntimeConfigBuilder` 合并生成 runtime config。这个 `.rules.yaml` 是持久化输入，下一次启动、切换配置或刷新订阅后仍会参与生成 `config.yaml`。
9. 规则集合 tab 支持读取 provider 名称、behavior、vehicleType、format、ruleCount、updatedAt，并调用 `PUT /providers/rules/{name}` 更新单个 provider，或批量更新全部 provider。
10. 失败时显示 toast，活动流记录错误详情，不把失败状态当成成功。

## 后续改进

2. 最近命中时间改成相对时间表达“刚刚 / N 分钟前 / 从未命中”。
3. 完善 Profile override 规则编辑器，支持 `no-resolve`、`src`、常见规则类型校验和现有 override 条目管理。
