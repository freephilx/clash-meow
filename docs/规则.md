# 规则

本文记录 DouClash 的规则展示、启停和后续编辑方案。这里的“规则”分两类：一类是 mihomo 运行时通过 controller 暴露的规则列表，另一类是 Profile YAML 里的 `rules` / `rule-providers` 配置原文。

## 添加规则对比

第三方对“添加规则”大致分成两类：

1. **运行时 inspect 型**：KumoApp、MetaCubeXD 更偏向查看和临时操作 `/rules`，不在规则页提供完整的新增规则入口。它们的优点是不会碰 Profile；缺点是不能表达“刷新订阅后仍保留这条本地规则”的长期意图。
2. **Profile override 型**：clash-party 的“编辑规则”会读取 Profile 原文和本地 rule override，把新增规则标记为 `prepend` 或 `append`，删除规则标记为 `delete`，最终写入单独的 override YAML；添加时用结构化表单选择 rule type、payload、proxy，并按规则类型显示 `no-resolve` / `src`。参考：[edit-rules-modal.tsx](https://github.com/mihomo-party-org/clash-party/blob/7ea11bb6452ea05a1d2b2eead0b7f001f05baef4/src/renderer/src/components/profiles/edit-rules-modal.tsx)。

DouClash 采用第二类，但不照搬完整规则列表编辑器。原因：

1. DouClash 已经把 Profile 原文和 runtime config 分开，新增规则天然应该进入 Profile override，而不是直接写订阅 YAML。
2. 规则页当前仍是运行时视图，不承载完整 YAML 编辑器；添加和修改使用轻量表单，并把结果保存为 Profile override。
3. 默认使用类型、匹配内容和策略三个结构化字段，避免 `MATCH,,DIRECT` 或漏填策略；复杂规则也可以切换“直接输入规则”，提交前至少校验规则类型、匹配内容和策略是否完整。
4. 入口使用规则页工具栏的 `+` 图标；承载使用 sheet，而不是独立 window。每条规则右侧的铅笔按钮和右键菜单提供修改入口。类型与策略候选在宽度不足时自动折行，底部预览始终显示最终规则文本。

## DouClash 推荐方案

DouClash 分阶段实现规则能力：

1. **规则页是运行时视图**：规则页展示 mihomo controller 当前 `/rules` 的真实结果，用于排障、观察命中和临时启停，不直接代表 Profile 原文。
2. **搜索与运行信息优先**：规则列表展示 type、payload、proxy、命中次数、未命中次数、命中率、最近命中 / 未命中和规则集合 size；页面只提供关键词搜索，不展示额外的类型、策略或排序筛选条。
3. **规则开关、新增和修改统一持久化到 Profile override**：关闭规则等价于在当前 Profile 的 `preferences.json.mihomoSettings.profiles[].ruleOverrides.delete` 中加入规则；重新启用等价于移除。新增规则默认写入 `prepend`。修改源规则等价于删除旧规则并前置新规则；修改已有本地 override 时直接替换旧 override。
4. **运行态使用最小热更新**：规则开关保存 override 后，当前运行态优先调用 mihomo `PATCH /rules/disable`。新增或修改规则保存 override 后调用 `PUT /configs?force=true` 热加载 runtime config。操作不重启 core；新增或修改的热更新失败时恢复旧 Profile override、旧 runtime config 和旧运行态。core 未运行时，override 和 runtime config 保留到下次启动生效。
5. **规则覆盖归属 Profile**：用户对规则的长期修改保存在对应 Profile 的元数据中，不修改订阅 YAML，也不建立第二份 override 文件。
6. **规则页保持单一列表**：页面只展示运行时规则，不提供“规则 / 规则集合”切换。刷新时仍读取 `rule-providers` 数据，供 `RULE-SET` 信息补充和后续能力使用。

## 持久化策略

DouClash 不直接编辑订阅 YAML，原因有三点：

1. 远程订阅刷新会覆盖本地修改，直接改原文容易让用户误以为订阅内容已经被服务端修改。
2. controller `/rules/disable` 使用 runtime index，而 index 会随订阅刷新、rule-providers 更新和配置 reload 改变，不能作为持久主键。
3. 完整规则编辑涉及 prepend / append / delete、`no-resolve`、`src`、rule-provider 与 override 合并顺序，应该在配置层统一设计，而不是塞进运行时 inspect 页。

规则修改采用统一的 Profile override 方案：

1. 用户在规则页关闭某条规则。
2. DouClash 用 controller `/rules` 返回的 `type`、`payload`、`proxy` 生成规则字符串，例如 `DOMAIN-SUFFIX,example.com,Proxy`；`MATCH` 这类空 payload 规则生成 `MATCH,DIRECT`。
3. DouClash 把该规则字符串写入当前 Profile 元数据的 `ruleOverrides.delete`。
4. 用户重新启用该规则后，从 `delete` 移除；三个数组都为空时保留空的逻辑覆盖集，不创建额外文件。
5. 新增规则默认插到 `ruleOverrides.prepend` 首位，确保最近添加的规则优先匹配；底层仍兼容已有 `append` 数据。
6. 新增和修改默认使用 `type`、`payload`、`proxy` 生成规则字符串，`MATCH` 不需要 payload。需要 `no-resolve`、`src`、逻辑组合或其他复杂参数时，使用“直接输入规则”。
7. `preferences.json` 中的逻辑结构为：
   ```json
   {
     "mihomoSettings": {
       "profiles": [{
         "id": "profile-id",
         "ruleOverrides": {
           "prepend": ["DOMAIN-SUFFIX,example.com,Proxy"],
           "append": ["DOMAIN-SUFFIX,tail.example.com,DIRECT"],
           "delete": ["DOMAIN-SUFFIX,old.example.com,DIRECT"]
         }
       }]
     }
   }
   ```
8. `prepend` 规则会插入到最终 runtime `rules` 前面，适合优先命中。
9. `append` 规则会追加到最终 runtime `rules` 后面，适合兜底补充。
10. `delete` 用规则字符串精确删除最终合并后的规则；因此它既能删除 Profile 原文规则，也能关闭通过 `prepend` / `append` 添加的规则。
11. Profile 原文仍保持不变。远程订阅刷新后，override 会继续参与 runtime config 生成，因此用户本地关闭或新增的规则不会因为刷新订阅而丢失。
12. 这个方案的取舍：相比只用 `/rules/disable`，override 不会把长期意图绑定到易变化的 runtime index；相比独立 override 文件，选择、元数据与规则覆盖共享同一份 Profile 状态；相比每次都重启或 reload 整份配置，规则开关只用 `/rules/disable` 修改当前运行态，新增或修改规则才 reload runtime config。

## 当前实现

当前代码实现运行时规则管理和 Profile 规则 override：

1. 侧边栏“翻墙”分组提供“规则”tab，显示在“日志”tab 上方。
2. 规则页进入或刷新时从 controller 读取 `/rules` 和 `/providers/rules`。`/rules` 兼容 mihomo 当前实测的数组响应，也兼容 MetaCubeXD 使用的 index 字典响应。
3. 页面只显示运行时规则列表，不展示规则集合切换、数量分段、排序或 facet 筛选条。
4. 规则页支持搜索 `type`、`payload`、`proxy`，列表顺序保持 controller 返回的配置顺序。
5. 每行显示规则类型、匹配内容、命中 / 未命中、size、命中率、最近命中 / 未命中和出站目标；已禁用规则降低透明度。右侧铅笔按钮可修改规则，右键菜单可复制或修改。
6. 开关规则时更新当前 Profile 的 `preferences.json.mihomoSettings.profiles[].ruleOverrides`：关闭写入 `delete`，启用时从 `delete` 移除。
7. 规则 override 更新后通过 `RuntimeConfigBuilder` 重新生成 runtime config。关闭 / 启用规则时，如果 core 正在运行，先调用 `PATCH /rules/disable` 修改当前运行态并刷新 `/rules`；如果该接口失败，再 fallback 到 `PUT /configs?force=true`。新增或修改规则时调用 `PUT /configs?force=true` 热加载并刷新 controller 数据，不自动重启 mihomo。
8. 规则页工具栏的 `+` 会打开添加规则 sheet；行内铅笔按钮打开修改 sheet。表单支持结构化输入和直接输入，新增规则写入 `prepend`；修改源规则写入“旧规则 delete + 新规则 prepend”。下一次启动、切换配置或刷新订阅后，这份 Profile 状态仍会参与生成 `config.yaml`。
9. 新增或修改的 metadata 写入、runtime 生成、Controller 热加载作为一个可回滚操作处理。任一步失败时恢复旧 override 和 runtime；已经尝试热加载时，再用旧 runtime 恢复运行态。
10. 后台保留 provider 读取和更新能力，但当前规则页不展示 provider 列表或更新入口。
11. 失败时显示 toast，活动流记录错误详情，不把失败状态当成成功。

## 后续改进

1. `RULE-SET` 行结合 `/providers/rules` 展示 provider `ruleCount`、更新时间和来源类型。
2. 最近命中时间改成相对时间表达“刚刚 / N 分钟前 / 从未命中”。
3. 为结构化编辑补充 `no-resolve`、`src` 等复杂参数控件；当前可以通过“直接输入规则”完成。
4. 需要时再评估规则集合管理和高级筛选入口，不在当前页面预留占位控件。
