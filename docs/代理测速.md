# 代理测速

本文记录 DouMeow “代理”页面的功能边界、数据来源和测速策略。代理页负责展示当前 mihomo 运行时代理组，支持切换代理，并为可选择的节点组提供手动测速。

## 数据来源

1. 节点组、当前选择、节点列表和历史延迟来自 mihomo controller 的 `/proxies`。
2. 本地 Profile 解析出的 `proxies` / `proxy-groups` 只用于离线预览和运行时数据缺失时的辅助展示。
3. 节点切换通过 mihomo controller 的 `PUT /proxies/{group}` 完成。
4. 直连模式下代理页只表达当前不使用代理组，不主动触发代理测速。

## 测速

代理测速的目标是回答“这个代理节点作为当前出站时，到指定 HTTP 测试地址的可用性和响应耗时如何”。它不是公网、DNS 或路由器诊断；这些指标属于 [互联网延迟](互联网延迟.md)。

### 开源项目对比

| 项目 | 做法 | 可借鉴点 |
| --- | --- | --- |
| ClashX.Meta | 菜单里的 Benchmark 会遍历可测速节点，通过 `GET /proxies/{proxy}/delay` 获取单节点延迟；失败时回传 `0`。测速 URL 存在用户设置里，默认是 `http://cp.cloudflare.com/generate_204`。参考：[ApiRequest.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/master/ClashX/General/ApiRequest.swift#L262-L273)、[ConfigManager.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/master/ClashX/General/Managers/ConfigManager.swift#L95-L99)、[ProxyGroupSpeedTestMenuItem.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/master/ClashX/Views/ProxyGroupSpeedTestMenuItem.swift#L99-L125)。 | 规则简单，兼容旧 controller；但大组逐节点测速会产生较多请求。 |
| clash-party | 同时封装单节点 `/proxies/{proxy}/delay`、组测速 `/group/{group}/delay` 和 provider healthcheck；测速 URL、超时、逐节点并发数都可配置；节点排序按最新 `history.delay`，空值和 `0` 放后面；托盘菜单对整组测速优先调用 `/group/{group}/delay`。参考：[mihomoApi.ts](https://github.com/mihomo-party-org/clash-party/blob/smart_core/src/main/core/mihomoApi.ts#L372-L397)、[proxies.tsx](https://github.com/mihomo-party-org/clash-party/blob/smart_core/src/renderer/src/pages/proxies.tsx#L98-L134)、[proxies.tsx](https://github.com/mihomo-party-org/clash-party/blob/smart_core/src/renderer/src/pages/proxies.tsx#L290-L352)、[tray.ts](https://github.com/mihomo-party-org/clash-party/blob/smart_core/src/main/resolve/tray.ts#L99-L121)。 | 功能完整，尤其适合 provider 节点和大节点组；但配置项偏多，容易让轻量客户端变复杂。 |
| KumoApp | Swift controller client 封装 `proxyDelay`，默认测试 URL 为 `https://www.gstatic.com/generate_204`、超时 `5000ms`；`groupDelay` 在 App 层按组遍历节点，失败时保留原节点 delay；节点列表用颜色区分正常、超时和未知延迟。参考：[MihomoControllerClient.swift](https://github.com/ProjectKumo/KumoApp/blob/main/Sources/KumoCoreKit/Networking/MihomoControllerClient.swift#L108-L132)、[KumoAppStore.swift](https://github.com/ProjectKumo/KumoApp/blob/main/Sources/KumoApp/Stores/KumoAppStore.swift#L555-L568)、[macos-swiftui-interface.md](https://github.com/ProjectKumo/KumoApp/blob/main/docs/interfaces/macos-swiftui-interface.md#L68-L79)。 | 和本项目技术栈最接近，展示策略稳定；但单纯逐节点测速在大组上效率不如 mihomo 组测速 API。 |

### 推荐方案

DouMeow 采用“按组触发、mihomo 优先、轻量降级”的方案：

1. 用户在节点组上点击“测速”时，只测试该节点组，不默认扫描所有组。
2. 代理测速依赖 mihomo external-controller；如果内核未启动，测速按钮仍允许点击，但只显示 toast“请先启动内核，再测试代理延迟”，不发起请求。
3. 优先调用 mihomo controller 的 `GET /group/{group}/delay`。这个路径由核心负责批量测速，能更好复用 mihomo 对组、provider 和历史结果的处理，也避免 App 自己制造大量并发请求。
4. 如果组测速 API 不可用、返回空结果或老版本核心不支持，则降级为逐节点 `GET /proxies/{proxy}/delay`。降级路径必须限制请求规模，避免对几百个节点同时发起测速。
5. 测速 URL 的优先级是：节点组自己的 `testURL`、默认 `https://www.gstatic.com/generate_204`。不要直接复用“互联网延迟诊断”的多 URL 设置，因为代理测速需要一个稳定、可被 mihomo controller 接受的 HTTP 测试目标。
6. 组测速超时时间根据节点数量动态放大，并限制在合理范围内；逐节点降级测速使用固定短超时。过短会误判弱网和远距离节点，过长会让代理页长时间处于“测速中”。
7. 成功延迟必须大于 `0`；`0` 或负数视为超时或不可用。
8. 合并结果时，新的有效延迟覆盖旧值；降级逐节点测速失败时可以保留旧的有效延迟，避免一次失败让列表闪成全空。组测速明确返回某节点失败时，应该把该节点标记为超时。
9. 测速期间同一时间只允许一个节点组处于测速状态，按钮显示进度并禁用重复点击。
10. 节点排序优先使用有效延迟从低到高；无有效延迟或超时节点排在后面；延迟相同再按节点名称排序。

### 为什么这样做

1. ClashX.Meta 的逐节点方式兼容性最好，但节点多时请求数量和 UI 等待时间会放大。本项目已经以 mihomo 为唯一运行时真相，应优先让核心做批量测速。
2. clash-party 的配置项和 provider healthcheck 很完整，但 DouMeow 当前定位是轻量 macOS 客户端，不需要一开始暴露并发数、provider 健康检查等高级开关。后续支持 proxy-provider 管理时，再补 provider 专用测速入口。
3. KumoApp 的 Swift 实现和展示方式适合借鉴：按组操作、失败时保持展示稳定、用颜色表达状态。本项目在此基础上增加 `/group/{group}/delay` 优先路径，兼顾稳定性和效率。
4. “互联网延迟”面板和“代理测速”必须分开。前者诊断本机网络环境，后者诊断代理节点；混在一起会让用户误以为公网慢就是节点慢，或节点超时就是本机网络不可达。
5. 如果后续要开放测速 URL、超时或降级并发数配置，应新增“代理测速”专用偏好，而不是复用“互联网延迟诊断”的偏好项。

### 当前实现要求

1. 代理页的“测速”按钮只对当前节点组生效。
2. 概览页可以在切换到非直连模式后，对主节点组触发一次轻量测速，用于刷新“当前节点”指标。
3. 所有测速结果最终写入运行时节点状态，供代理页、概览页和互联网延迟面板读取。
4. 文案保持明确：未知显示 `--`，超时显示“超时”，有效值显示 `N ms`。
5. 后续如果实现 proxy-provider 管理，provider 节点应优先走 `/providers/proxies/{provider}/{proxy}/healthcheck`，普通节点继续走当前策略。
