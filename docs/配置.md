# 配置

本文记录“配置文件被本地修改后”的处理策略。这里的本地修改包括用户用编辑器修改当前 Profile YAML、修改 App 生成的运行时 `config.yaml`，以及 App 自己因为 TUN、模式、端口等设置写入运行时配置。

## 第三方对比

| 项目 | 本地修改处理 | 失败处理 | 对 Clash Meow 的启发 |
| --- | --- | --- | --- |
| ClashX.Meta | 监听当前 YAML 文件。当前配置名变化后重新监听对应文件；文件 `modified` 或 `renamed` 时发出配置变更通知，再通过 `ConfigReloadManager.updateConfig()` 调 controller reload。参考：[ConfigManager.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/9a9432aa82a7e92dac81d94c7ba02871b9d3c70e/ClashX/General/Managers/ConfigManager.swift)、[ConfigFileManager.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/9a9432aa82a7e92dac81d94c7ba02871b9d3c70e/ClashX/General/Managers/ConfigFileManager.swift)、[ConfigReloadManager.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/9a9432aa82a7e92dac81d94c7ba02871b9d3c70e/ClashX/General/Managers/ConfigReloadManager.swift)。 | reload 失败时展示错误，不把失败配置当成已成功运行。 | 适合“用户直接编辑当前 YAML”的轻量体验；需要有暂停一次自写事件的机制，避免 App 自己写入也触发外部修改流程。 |
| KumoApp | Profile 原文由 `ProfileRepository` 保存，运行时配置由 `RuntimeConfigBuilder` 生成到工作目录；core 启动时使用生成后的 runtime config。DNS、TUN、Sniffer 等 App 接管配置是 staged/apply，而不是直接让订阅 YAML 覆盖。参考：[ProfileRepository.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCoreKit/Configuration/ProfileRepository.swift)、[RuntimeConfigBuilder.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCoreKit/Configuration/RuntimeConfigBuilder.swift)、[CoreSupervisor.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCoreKit/Runtime/CoreSupervisor.swift)。 | App 内更新当前 Profile 后会重新激活当前 Profile；运行中应用 TUN/DNS 等设置会重启或等待 controller ready。参考：[KumoAppStore.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoApp/Stores/KumoAppStore.swift)。 | 更适合 Clash Meow 的长期架构：Profile 是输入，runtime config 是输出；本地编辑 Profile 后重新生成 runtime，而不是把订阅文件直接当最终运行配置。 |
| clash-party | Profile 切换串行执行；可选 hot reload，默认重启 core。`setProfileStr()` 写入当前 Profile 后先尝试 `mihomoHotReloadConfig()`，失败再 fallback restart。切换 Profile 失败会回滚 `current`。参考：[profile.ts](https://github.com/mihomo-party-org/clash-party/blob/7ea11bb6452ea05a1d2b2eead0b7f001f05baef4/src/main/config/profile.ts)、[mihomoApi.ts](https://github.com/mihomo-party-org/clash-party/blob/7ea11bb6452ea05a1d2b2eead0b7f001f05baef4/src/main/core/mihomoApi.ts)、[en-US.json](https://github.com/mihomo-party-org/clash-party/blob/7ea11bb6452ea05a1d2b2eead0b7f001f05baef4/src/renderer/src/locales/en-US.json)。 | hot reload 失败时尝试重启；Profile 切换失败回滚当前选择。 | 值得借鉴“串行化 + hot reload 优先 + restart fallback + current 回滚”，避免多次保存或多次切换造成状态漂移。 |

## Clash Meow 推荐方案

Clash Meow 采用“Profile 原文可编辑、runtime config 可再生、App 受控字段优先”的策略：

1. **Profile 是用户输入**：`profiles/<id>.yaml` 保留用户导入或远程下载的原文。用户用编辑器修改当前 Profile 时，App 应把它当成外部输入变化。
2. **runtime config 是运行输出**：`~/.config/clash-meow/config.yaml` 由 `RuntimeConfigBuilder` 根据 Profile + App 设置生成。它可以供排障查看，但不应作为长期手工维护的主入口。
3. **App 受控字段最终覆盖**：controller、mode、allow-lan、log-level、TUN、DNS、Sniffer 等由 App 接管的字段，不允许被订阅或手工 Profile 修改永久覆盖。`mixed-port` 默认继承 Profile；只有 App 提供明确端口偏好时才覆盖。
4. **本地修改先校验再应用**：检测到当前 Profile 被外部修改后，先 debounce，使用 Yams 解析并生成 runtime config，再通过 mihomo reload 或 restart 校验。成功后更新 UI、代理组和日志；失败时保留上一次可运行的 runtime 状态，并提示错误。
5. **App 自写不触发外部修改流程**：导入、刷新远程订阅、切换 Profile、TUN/模式/端口等 App 主动写入时，需要短暂 suppress 文件监听事件。
6. **串行化处理**：配置切换、远程刷新、本地文件变更和 TUN 应用不能并发 reload。后来的事件可以取消或合并前一个 debounce，但真正应用阶段必须单飞。
7. **失败不提交状态**：如果生成或 reload 失败，不更新“已应用成功”的 UI 状态，不覆盖用户偏好，不切换 current profile；需要记录 app 日志并显示 toast。
8. **运行时配置被手改只做一次性应用**：如果用户直接修改 `config.yaml`，App 可以尝试 reload 作为高级排障入口；但这次修改不写回 Profile。下一次切换配置、刷新订阅或修改 App 设置时，runtime config 会被重新生成。

## 当前实现要求

当前代码应保持以下行为：

1. 监听当前 `config.yaml` 和当前 Profile YAML。
2. 监听事件 debounce，避免编辑器保存过程中的短暂半成品反复 reload。
3. 对 App 自己触发的写入使用 suppress 窗口，避免误判为外部修改。
4. 当前 Profile YAML 被修改后，重新激活 Profile，生成 runtime config，并 reload/restart core。
5. runtime config 被修改后，重新读取快照并应用，但不反向写入 Profile。
6. 应用成功后刷新 Profile 列表、代理预览和 controller 数据。
7. 应用失败时 toast 提示，并保留旧的可运行状态。
8. 配置页列表卡片展示的是 YAML 文件当前事实，例如 `mixed-port`、`mode`、`allow-lan`、`tun.enable`；这些字段不能被旧的运行态缓存覆盖，避免用户已经修改文件但卡片仍显示旧端口。
9. 启动前释放端口只读取顶层监听字段和顶层 `dns.listen`；代理节点里的 `port: 443` 不是本机监听端口，不能被误释放。
10. App 启动恢复选中 Profile 时，必须校验 runtime `config.yaml` 是否等于当前 Profile 重新生成的结果；如果不一致，要先重写 runtime，再启动 mihomo，避免旧 runtime 继续监听旧端口。
11. 配置页点击卡片只用于查看，不触发配置切换；切换配置必须通过卡片右侧的“使用配置”开关明确执行。
12. 配置页支持直接拖入 `.yaml` 或 `.yml` 文件；拖放导入与“打开本地 YAML”共用同一条导入、校验和激活流程。
13. 配置更新时间使用简体中文相对时间；一分钟内显示“刚刚”，其余显示完整的相对时间。

## runtime config 更新时机

`~/.config/clash-meow/config.yaml` 是 runtime config，它不是用户长期维护的源文件。冷启动、切换配置和当前 Profile 变更都必须通过同一条路径生成它：

```text
当前 Profile YAML + App 设置
  -> RuntimeConfigBuilder
  -> ~/.config/clash-meow/config.yaml
  -> mihomo 启动或 reload
```

具体更新规则：

1. **每次冷启动都校验**：App bootstrap 时先恢复选中的 Profile，再用当前 Profile 重新生成一份 runtime YAML，并与磁盘上的 `config.yaml` 比较。不一致时立即重写，然后才允许自动启动 mihomo。
2. **App 启动前修改了当前 Profile YAML**：冷启动校验会发现 runtime 已过期并重写，所以用户离线修改 `profiles/<id>.yaml` 后不会继续使用旧端口或旧规则启动。
3. **App 运行中修改当前 Profile YAML**：文件监听 debounce 后重新激活当前 Profile，生成 runtime config，并 reload/restart mihomo。
4. **App 运行中修改非当前 Profile YAML**：不立即改 runtime；切换到该 Profile 或冷启动恢复它时再生成 runtime。
5. **切换、导入、刷新当前 Profile**：立即生成新的 runtime config。远程订阅刷新如果不是当前 Profile，只更新 Profile 原文和元数据。
6. **修改规则页里的规则开关**：写入当前 Profile 的 `profiles/<id>.rules.yaml` override。关闭规则写 `delete:`，重新启用规则从 `delete:` 移除，然后重新生成 `config.yaml`；不再写 `settings.json.disabledRules`，也不回放旧数据。
7. **新增配置规则**：写入当前 Profile 的 `profiles/<id>.rules.yaml` override 的 `prepend:` / `append:`，再重新生成 `config.yaml`；不修改远程订阅原文。
8. **修改 TUN 等 App 接管设置**：当前会写入 runtime config，并通过 hot reload 或 restart 校验生效。后续 DNS/Sniffer 等 UI 设置也应走 RuntimeConfigBuilder，而不是直接改 Profile 原文。

这条规则的目的，是让用户可编辑的 Profile 和 mihomo 实际使用的 runtime 始终可解释：Profile 是输入，runtime 是输出；冷启动前无论用户是否曾在 App 外修改 YAML，都不会继续使用旧的 runtime。

runtime config 相关动作必须写日志，方便排查“Profile 是 7891 但启动仍释放 7890”这类问题：

1. 日志模块使用 `RuntimeConfig`。
2. 写入 `logs/app.log`，因此在日志页选择“应用”或“全部”可以看到。
3. Debug 构建同时 `print("[RuntimeConfig] ...")`，因此 Xcode console 也能看到。
4. 每次写入 runtime config 时至少记录 `reason`、`profile`、`path`、`mixed-port`、`external-controller` 和字节数。
5. 冷启动校验时，即使 runtime 已是最新，也记录一条“已是最新”的检查日志。

## 后续改进

1. 为配置变更增加单独状态，例如“检测到本地修改 / 正在校验 / 已应用 / 应用失败”。
2. 对外部修改失败保留错误详情入口，显示 mihomo 校验错误和文件路径。
3. 在 `config.yaml` 顶部写入注释，说明它是生成文件，推荐修改 Profile 原文或 App 偏好。
4. 对当前 Profile 外的 YAML 修改只更新列表元数据，不自动应用。
5. 为 reload 失败增加旧 runtime config 备份恢复，避免坏配置覆盖最后一次可运行配置。
