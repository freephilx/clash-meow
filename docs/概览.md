# 概览页面

本文记录 dou-meow “概览”页面的功能、数据来源和当前规则。概览页是 App 的默认入口，用来集中展示当前配置、内核运行状态、出口策略、节点选择、系统接管状态和实时活动数据。

## 页面结构

概览页从上到下由这些区域组成：

1. 远程配置用量与内核总开关
2. 出口模式
3. 配置节点
4. 系统代理
5. 增强模式
6. 活动区：延迟、上传、下载、活动连接、总流量、流量列表

页面入口在左侧导航“常用 / 概览”。打开 App 后默认选中概览页。

## 配置与内核卡片

顶部卡片展示当前配置文件和内核运行状态。

显示内容：

1. 当前 Profile 名称。
2. `YAML` 类型标记。
3. 远程配置用量信息。
4. 用量进度条。
5. 到期时间或最后更新时间。
6. 内核总开关。
7. “刷新”和“配置”快捷操作。

配置名称规则：

1. 优先显示当前 Profile 名称。
2. 如果没有当前 Profile，则显示当前 core config 文件名。

用量规则：

1. 用量来自当前 Profile 的 `subscriptionUserInfo`。
2. 如果远程订阅返回了总量，主数值显示已使用量，次级数值显示总量。
3. 详情文案显示：

```text
已使用 / 总量 · 百分比
```

4. 如果订阅只返回已使用量、总量为 0，则显示：

```text
已使用 <用量>
```

5. 如果当前 Profile 是本地 YAML，没有订阅用量，则显示“本地 YAML 没有远程配置用量信息”。
6. 如果当前 Profile 是远程配置但没有返回用量，则显示“远程配置没有返回用量信息”。
7. 没有用量时，进度条显示为空态。

页脚时间规则：

1. 如果订阅有 `expire` 且大于 0，显示到期日期。
2. 否则如果 Profile 有 `updatedAt`，显示最后更新日期。
3. 否则显示“导入或刷新远程配置后显示真实用量”。
4. 日期格式为 `yyyy-MM-dd`。

内核总开关规则：

1. 右上角总开关名称为“内核总开关”。
2. 开关开启时调用 `state.connect()` 启动内核。
3. 开关关闭时调用 `state.disconnect()` 停止内核。
4. 开关状态会持久化到 `~/.config/dou-meow/preferences.json` 的 `coreEnabled` 字段。
5. 下一次打开 App 时，如果 `coreEnabled` 为 `true`，启动流程会自动启动内核；如果为 `false`，保持停止。
6. 关闭内核总开关时，系统代理和 TUN 会联动关闭，并把实际状态写为关闭。
7. 联动关闭不是用户对系统代理或 TUN 的主动操作，不会覆盖 `systemProxyUserEnabled` 和 `tunUserEnabled`。
8. 再次打开内核总开关时，系统代理和 TUN 会按用户最后一次主动设置恢复。
9. 内核处于 `starting` 时，总开关显示为开启但禁用交互，避免用户看到开启后又跳回关闭。
10. 启动内核后，必须等 mihomo controller 可用，才能恢复系统代理、TUN 和实时流量连接。
11. 启动、重启或配置切换前，App 会按当前 YAML 检查监听端口；只有端口确实被占用时才处理端口释放。
12. 端口释放先使用普通权限终止当前用户可管理的旧进程，只有普通权限释放失败时才请求 privileged helper。
13. 端口检查会排除当前正在运行的 mihomo 进程，避免配置重载时把自己的内核当成冲突进程处理。
14. 如果 privileged helper 安装授权被取消或失败，本次 App 会话会短时间暂缓重复请求管理员授权，避免连续弹出密码窗口。
16. 右侧状态点颜色：
   - `running`：紫色。
   - `starting`：橙色。
   - `failed` 或 `missingBinary`：红色。
   - `stopped`：灰色。

快捷操作：

1. “刷新”：调用 `state.refresh()`，从 mihomo controller 读取版本、配置、连接、节点组、规则和当前流量。
2. “配置”：跳转到“配置”页面。

## 出口模式

出口模式卡片用于选择当前网络流量的处理策略。

可选模式：

1. `RULE / 规则`：按规则匹配节点组与出站线路。
2. `ALL / 全局`：所有连接使用全局节点组选择。
3. `DIR / 直连`：所有连接直接出站，不经过节点组规则。

选中规则：

1. 如果内核正在运行，页面显示 controller 当前 `config.mode` 对应的模式。
2. 如果内核未运行，页面显示本地保存的 `forwardingMode` 偏好。

点击规则：

1. 点击某个模式会调用 `state.setForwardingMode(...)`。
2. 内核运行时，会通过 controller `PATCH /configs` 同步模式。
3. 内核未运行时，只保存本地偏好，等待下次启动后同步。
4. 切换失败时，刷新 controller 状态并回滚 UI 模式。
5. 切换成功后，如果不是直连模式，会对概览页主节点组触发一次延迟测试。

## 配置节点

代理页展示策略见 [代理显示](代理显示.md)，测速策略见 [代理测速](代理测速.md)。

配置节点卡片展示当前选择和低延迟服务器，最多展示 3 个节点。

节点来源：

1. 优先使用运行时 controller 返回的 proxy groups。
2. 如果 controller proxy groups 为空，则使用当前 Profile 解析出的 proxy groups。
3. 节点详情来自当前 Profile 的 `proxies` 列表和运行时测速状态。

展示规则：

1. 直连模式下，概览节点列表只显示 `DIRECT`。
2. 全局模式下，优先使用 `GLOBAL` 节点组；如果配置没有声明 `GLOBAL`，App 会根据 Profile 节点合成一个 `GLOBAL` 组。
3. 规则模式下，优先使用第一个非 `GLOBAL` 节点组。
4. 第一个展示项优先是当前选中节点。
5. 其余节点按有效延迟从低到高排序。
6. 延迟相同或都没有有效延迟时，按节点名称排序。
7. 无效延迟包括空值、0 或负数。
8. 如果当前配置没有声明 `proxies` 节点，显示“当前配置未声明 proxies 节点”。

节点行内容：

1. 左侧显示节点类型前三个字符，例如 `VME`、`TRO`、`HYS`。
2. 当前选中代理显示“当前选择 · 延迟”。
3. 非选中代理显示“延迟 · endpoint”。
4. endpoint 来自节点 server 和 port；如果缺失则退化为 server、port 或“配置节点”。

点击规则：

1. 点击节点会使用当前主节点组调用 `state.selectProxy(groupID:proxyName:)`。
2. 全局模式下，主节点组优先为 `GLOBAL`。
3. 非全局模式下，主节点组为第一个可用节点组。
4. “查看全部”跳转到“代理”页面。

## 系统代理

系统代理卡片控制 macOS 系统代理接管。

显示内容：

1. 标题：系统代理。
2. 说明：大多数应用的流量可以通过系统代理设置接管，兼容性和性能更稳定。
3. 状态文案：
   - `已设置`：系统代理实际已启用。
   - `未设置`：开关关闭。

开关规则：

1. 开关绑定到 id 为 `proxy` 的 feature toggle。
2. 切换时调用 `state.setToggle(proxyToggle, isOn:)`。
3. 启用系统代理时使用当前 mixed-port，默认端口为 `7890`。
4. 系统代理偏好会在启动流程里按保存状态自动应用。
5. 用户主动开启或关闭成功后，会同时写入 `systemProxyUserEnabled` 和 `systemProxyEnabled`。
6. 内核总开关联动关闭系统代理时，只把 `systemProxyEnabled` 写为关闭，不覆盖 `systemProxyUserEnabled`。
7. 如果用户开启或关闭系统代理失败，或当前状态不允许开启，会显示 toast，并把开关、概览状态和偏好恢复到修改前的状态。

## 增强模式

增强模式卡片控制 TUN 接管。

显示内容：

1. 标题：增强模式。
2. 说明：未遵循系统代理的应用可经由 TUN 或规则引擎接管，保持所有流量由 DouMeow 路由。
3. 状态文案：
   - `已启用`：TUN 开启。
   - `已禁用`：TUN 关闭。

开关规则：

1. 开关绑定到 id 为 `tun` 的 feature toggle。
2. 切换时调用 `state.setToggle(tunToggle, isOn:)`。
3. TUN 状态优先读当前 toggle；没有 toggle 时读 `TunPreference.isEnabled`。
4. TUN 相关配置来自当前展示配置里的 `tun` section，设备名缺省为 `utun10`。
5. 用户主动开启或关闭成功后，会同时写入 `tunUserEnabled` 和 `tunEnabled`。
6. 内核总开关联动关闭 TUN 时，只把 `tunEnabled` 写为关闭，不覆盖 `tunUserEnabled`。
7. 用户主动开启增强模式必须以内核已启动为前提；如果内核未启动，显示“请先启动内核”，并把开关和偏好恢复到修改前。
8. 如果启动 App 时内核总开关是关闭的，`tunEnabled` 会被修正为关闭；`tunUserEnabled` 保留用户意图，下一次打开内核总开关时再恢复。
9. 增强模式通过 `RuntimeConfigBuilder` / `Yams` 结构化写入受控 runtime config 后，优先调用 mihomo `PUT /configs?force=true` 热重载，再用 `GET /configs` 校验运行时 `tun.enable`。
10. 如果热重载失败、超时或运行时校验不一致，会 fallback 到重启内核并再次校验。
11. App bundle 下 mihomo 的启动、停止和重启统一通过 privileged helper 以 root 执行，确保 macOS 允许创建 `utun` 和配置路由。
12. 增强模式应用过程中会抑制 App 自己写入 runtime config 触发的文件监听事件，避免授权或重启耗时较长时被误判为外部配置修改。
13. 如果重启后仍失败，App 会写回修改前的 runtime config，把按钮、`tunEnabled` 和 `tunUserEnabled` 恢复到修改前，并提示 TUN 设置失败。
14. 概览页开关不能先把本地 toggle 固定为目标值；必须以 `AppState` 校验和回滚后的状态为准，避免内核停止时 UI 仍显示已启用。

## 活动区

活动区显示当前网络运行数据，数据主要来自 controller 的 `/traffic`、`/connections` 和代理测速结果。

### 互联网延迟

详细设计见 [互联网延迟](互联网延迟.md)。

显示内容：

1. 主数值：公网 HTTP `HEAD` 测试平均延迟。
2. 路由器：默认网关 ICMP ping 延迟。
3. DNS：`dig bing.com A` 查询耗时。
4. 当前节点：当前选中代理节点延迟。
5. “诊断”按钮。

规则：

1. 面板首次出现且没有诊断结果时，自动执行一次互联网延迟诊断。
2. “诊断”按钮和刷新图标调用 `diagnoseInternetLatency()`。
3. 诊断期间展示加载状态，并禁止重复触发。
4. 公网、路由器、DNS 任一项失败时，对应位置显示 `--`。
5. 当前节点延迟优先来自 `proxyNodeStatuses[selected].delay`。
6. 如果测速状态没有有效延迟，则回退到节点组里当前节点的 delay。
7. 节点延迟必须大于 0，否则显示 `--`。

### 上传与下载

上传、下载卡片展示实时速率和趋势线。

数据规则：

1. 上传速率来自 `state.traffic.up`。
2. 下载速率来自 `state.traffic.down`。
3. 单位由 byte formatter 自动转换为 B、KB、MB、GB。
4. 趋势线来自 `trafficHistory`：
   - 上传卡片使用 `trafficHistory.upload`。
   - 下载卡片使用 `trafficHistory.download`。
5. `trafficHistory` 最多保留 60 个采样点。
6. 内核停止或 traffic stream 失败时，实时流量和趋势线会清空。

### 活动连接

活动连接卡片展示当前连接数量和进程数。

规则：

1. 主数值为 `connections.connections.count`。
2. “进程”数量按连接的 `processName` 去重；如果没有进程名，则使用连接 host。
3. “设备”和“DHCP 设备”当前为 TODO。
4. 状态点：
   - 内核运行：紫色。
   - 内核未运行：橙色。

### 总流量

总流量卡片展示当前会话累计流量。

规则：

1. 默认展示“今日”。
2. “本月”当前为 TODO。
3. 主数值优先使用 `/traffic` stream 中的 `upTotal + downTotal`。
4. 如果 stream 累计值为 0，则回退到 `/connections` 的 `uploadTotal + downloadTotal`。
5. “直连”和“节点”拆分当前为 TODO。

### 流量列表

流量列表卡片展示客户端维度的流量排行。

显示内容：

1. 顶部范围切换：`全部`、`节点`。
2. 时间条：使用 `trafficHistory.total` 绘制柱状时间线。
3. 维度切换：`客户端`、`域名`、`策略`。
4. 排行列表。

规则：

1. 当前只有 `全部 / 客户端` 维度已实现。
2. 客户端行来自当前连接列表。
3. 每个客户端的流量为该客户端所有连接的 `upload + download`。
4. 客户端名优先使用 `processName`；没有进程名时使用连接 host。
5. 只展示流量最高的前 5 个客户端。
6. 选择 `节点` 时显示“节点流量筛选尚未实现”。
7. 选择 `域名` 或 `策略` 时显示“该维度统计尚未实现”。
8. 没有数据时：
   - 内核运行：显示“暂无客户端流量数据”。
   - 内核未运行：显示“启动内核后可查看流量统计”。

## 数据刷新规则

概览页依赖 `AppState` 的全局数据刷新机制。

启动流程：

1. `bootstrap()` 会准备 core 环境。
2. 如果启用了 dashboard demo，则填充演示数据并停止真实刷新。
3. 正常模式下会刷新 Profile 列表、读取当前 Profile 快照、启动配置文件监听。
4. 如果开启了内核自动启动，则启动 core。
5. core 启动后等待 controller 可用，再调用 `refresh()` 并恢复保存的网络偏好，例如系统代理和 TUN。

`refresh()` 读取的数据：

1. `version`
2. `configs`
3. `connections`
4. `proxies`
5. `rules`
6. `traffic`

刷新成功后：

1. 更新 controller endpoint。
2. 更新连接、规则、当前流量。
3. 根据 controller proxies 生成节点组。
4. 合并节点延迟状态，避免新数据缺失时覆盖已有有效延迟。
5. 同步 traffic stream。
6. 同步保存的出口模式和 allow-lan 设置。

traffic stream 规则：

1. core 健康运行时启动 `/traffic` WebSocket。
2. 收到快照后更新当前速率和趋势采样。
3. core 停止时取消 stream 并清空流量数据。
4. stream 出错时清空流量数据。

## 演示数据

概览页支持演示入口：

1. `-dashboardDemo` 启动参数：直接填充演示状态。

演示数据包含：

1. 版本、配置、系统代理、TUN、出口模式。
2. 订阅用量。
3. 实时上传、下载、累计流量和趋势线。
4. 活动连接。
5. Profile、节点组、节点延迟。

这些数据用于截图、调试和展示，不代表真实 controller 状态。
