# 日志架构

DouMeow 的日志存储、内存发布和实时跟随逻辑与 douwork 保持一致，同时继续使用 `~/.config/dou-meow/` 作为应用数据根目录。

## 路径

```text
~/.config/dou-meow/runtime/logs/app.log
~/.config/dou-meow/runtime/logs/app-<timestamp>.log
~/.config/dou-meow/runtime/mihomo/mihomo.log
```

`app.log` 保存 DouMeow 自身事件；`mihomo.log` 接收 Mihomo 的 stdout 和 stderr。两类日志不会混写。

## 应用日志

应用日志经过两条链路：

1. `AppLogSupport` 生成包含本机时区、级别、模块和消息的结构化日志。
2. 日志通知统一投递到主队列，再发布到 `AppState.appLogs`；后台下载或解析任务写日志时不会跨队列更新 UI，日志页也无需刷新即可看到。
3. 同一行交给专用串行队列异步写入 `app.log`。
4. App 退出前同步刷新文件句柄。

内存只保留当前 App 会话最近 500 条应用日志。App 重新启动后不会把归档应用日志重新加载到页面。

用户主动生成[网络诊断报告](网络诊断.md)时，会在刷新写入队列后有界读取当前日志和最近 3 份归档；这不会把历史归档重新载入日志页面。

文件治理规则：

1. App 启动时把已有 `app.log` 轮转为 `app-yyyyMMdd-HHmmss-SSS.log`。
2. 最多保留 9 个归档文件，加上当前 `app.log` 共 10 个运行日志文件。
3. 当前文件上限固定为 10 MiB；超限后保留最近约 5 MiB。
4. 单行最多 64 KiB，超长内容会被截断并添加标记。
5. 新文件权限为 `0600`。

## Mihomo 日志

`MihomoCoreManager` 启动 Mihomo 时，以追加方式把 stdout 和 stderr 指向 `runtime/mihomo/mihomo.log`。App 不再写入自定义 session header，也不对该文件做原地大小截断。

日志页刷新时：

1. 从文件尾部逆向读取，最多扫描 1 MiB。
2. 最多解析最近 500 行。
3. 只保留时间戳晚于本次 App 启动时间的 Mihomo 日志。
4. 不读取整个文件，避免大日志文件造成明显内存和主线程压力。

内核日志由独立的 `MihomoLogStore` 发布，与应用日志内存数组分开管理。

## 实时跟随

日志页在未暂停、来源不是“应用”且 Mihomo 正常运行时连接：

```text
ws://127.0.0.1:9090/logs?level=<level>&format=structured
```

行为规则：

1. 单条 WebSocket 消息最大 1 MiB，超限消息直接丢弃。
2. 收到的日志先进入待发布队列，每 100 ms 批量更新一次 UI。
3. `MihomoLogStore` 最多保留 500 条内核日志。
4. 连接断开后重新读取 `mihomo.log`，再按 1、2、4、8 秒退避重连。
5. 收到有效日志后，重连等待恢复为 1 秒。
6. 暂停、切到“应用”、离开日志页或停止内核时，立即取消连接并刷新待发布日志。
7. WebSocket 日志只进入内存，不重复写入 `mihomo.log`。

## 页面合并

日志页把 `AppState.appLogs` 和 `MihomoLogStore.entries` 转换为统一时间线，但不改变底层分离存储：

1. 默认来源和级别均为“全部”。
2. 应用与内核日志按时间倒序交错显示。
3. 相邻且来源、级别、消息相同的日志折叠为一组。
4. 支持搜索、来源筛选、级别筛选、暂停、刷新和复制原始日志。
5. 刷新只重新读取 Mihomo 文件日志；当前会话应用日志持续保留在内存中。
