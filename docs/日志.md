# 日志查看流程

本文先给出 clash-meow 的推荐方案和落地步骤；第三方实现放在后面，作为方案依据和取舍参考。

## 推荐方案

clash-meow 应采用“应用日志与内核日志分离存储、日志页同时支持历史读取和实时跟随、文件带滚动治理”的方案。

目标：

1. 用户打开日志页时，能立刻看到最近历史日志。
2. 用户需要实时排查时，可以跟随 mihomo `/logs` WebSocket。
3. 日志文件不能无限增长。
4. 应用自身问题和 mihomo 内核问题要能区分。
5. 日志页的“清空视图”和“清空文件”语义要明确分开，避免误删排障信息。

具体设计：

1. 保留当前 `core.log` 作为 mihomo stdout/stderr 的持久日志。
2. 增加 `app.log`，记录 clash-meow 自身事件，例如启动、停止、配置切换、端口释放、helper 调用、WebSocket 重连、日志文件清理结果。
3. 日志页默认展示 `core.log` 最近 500 行，保持当前体验。
4. 日志页增加来源筛选：
   - `core`：mihomo stdout/stderr 和 `/logs` 实时日志。
   - `app`：clash-meow 自身日志。
   - `all`：合并展示。
5. 日志页的“跟随”继续连接 mihomo `/logs?level=...`，实时追加到 UI。
6. 实时日志可以只进入 UI 内存，不强制再写入 `core.log`，避免 stdout/stderr 和 `/logs` 双重记录同一类内核日志。
7. 增加“打开日志文件”和“在 Finder 中显示”按钮，方便用户把日志发给开发者。
8. 增加两个清理动作：
   - “清空视图”：只清空 `state.logs`。
   - “清空日志文件”：需要二次确认，截断当前选中来源的日志文件。
9. 增加日志文件治理：
   - 单文件大小上限默认 10MB。
   - 达到上限后保留最近内容并写入截断标记。
   - 可选保留天数默认 7 天。
   - 启动时清理过期日志。
10. 日志时间必须按本机当前时区显示：
    - `app.log` 写入时使用本机时区时间，并带上时区偏移。
    - `core.log` 的 App 启动 session header 使用本机时区时间。
    - 从 mihomo `/logs` WebSocket 收到的 `time` 字段，如果带有 UTC 或其他时区偏移，日志页展示前转换成本机时区。
    - 历史日志读取时，能解析的 ISO8601 时间统一转换成本机时区；无法解析的原样显示，避免丢失信息。
    - 日志文件里的时间保留 `+08:00` 这类偏移；日志页为了避免用户误读，展示为 `yyyy-MM-dd HH:mm:ss`。

保留策略：

1. 默认最多保留 7 天日志。
2. App 重启后，之前的日志仍然存在，因为日志写在 `~/.config/clash-meow/runtime` 下的文件中，不依赖 UI 内存。
3. 日志页重启后应先读取文件里的最近历史日志，再按需开启实时跟随。
4. 超过保留天数的旧日志在 App 启动时清理。
5. 单个日志文件超过大小上限时，只截断较早内容，保留最近内容。
6. 用户点击“清空视图”不会影响重启后的历史日志；只有“清空日志文件”才会删除或截断持久日志。

偏好设置：

需要用户修改的日志策略放到“偏好设置”里，详见 `docs/偏好设置.md`。建议暴露这些选项：

1. 日志保留天数，默认 7 天。
2. 单文件大小上限，默认 10MB，最小 1MB。
3. 是否记录应用日志，默认开启。
4. 日志页默认来源，默认 `core`。
5. 日志页默认级别，默认跟随当前 mihomo `log-level`。
6. 是否启动时自动清理过期日志，默认开启。
7. 是否显示“清空日志文件”危险操作，默认开启但需要二次确认。

实施步骤：

1. 抽出日志路径定义，例如 `coreLogFile`、`appLogFile`、`logsDirectory`，避免路径散落在多个类型里。
2. 新增 `AppLogSupport`：
   - 提供 `info`、`warning`、`error`、`debug` 写入方法。
   - 每行带时间、级别、模块、消息；时间使用本机时区并保留时区偏移。
   - 写入 `~/.config/clash-meow/runtime/logs/app.log`。
3. 新增通用 capped append 工具：
   - 写入前检查文件大小。
   - 超限时保留尾部内容。
   - 插入类似 `[LOG] File truncated because size limit reached.` 的标记。
4. 修改 `MihomoCoreManager.openLogFileHandle()`：
   - 继续 append 到 `core.log`。
   - 写 session header 前先经过大小治理。
5. 在关键流程补充 app 日志：
   - 应用启动和退出。
   - mihomo start/stop/restart。
   - 端口释放成功/失败。
   - helper 安装、版本读取、XPC 调用。
   - `/logs` WebSocket 连接、断开、错误。
   - 配置切换、热更新、模式切换失败。
6. 扩展 `CoreLogEntry` 或新增 `AppLogEntry`，带上 `source` 字段。
7. 修改 `CoreLogSupport.recentLogs`，支持读取指定文件并标记来源。
8. 修改日志页：
   - 增加来源筛选。
   - 保留级别筛选、搜索、刷新、跟随。
   - 增加“打开文件”“在 Finder 中显示”“清空文件”。
9. 增加启动清理：
   - 默认清理 7 天前的日志。
   - 只匹配 clash-meow 自己的日志文件。
10. 补测试：
   - 日志级别推断。
   - capped append 超限保留尾部。
   - 清空视图不删除文件。
   - 清空文件会截断目标文件。
   - app/core 来源筛选正确。
   - 日志时间按本机时区格式化和展示。

理由：

1. 当前 clash-meow 已经有历史文件和实时流，保留这条主线改动最小。
2. 只打开外部日志文件不够好，用户排查时仍然需要 App 内搜索、筛选和跟随。
3. 只展示实时流也不够好，用户打开页面前的启动失败、端口占用、core 崩溃信息会丢失。
4. app 日志和 core 日志分离后，能快速判断问题在 UI/控制层还是 mihomo 内核。
5. 文件大小和保留天数治理可以避免 `core.log` 长期无限增长。
6. “清空视图”和“清空文件”分开，可以降低误删关键日志的风险。
7. 这个方案吸收了 KumoApp 的组件分文件、clash-party 的文件治理、ClashX.Meta 的便捷打开文件，同时保留 clash-meow 当前日志页的可交互体验。

## clash-meow 当前基础

clash-meow 目前采用“文件历史 + WebSocket 实时流”的方式，UI 内直接展示日志，而不是像 ClashX.Meta 那样打开外部日志文件。

相关代码：

- `clash-meow/Sources/ClashMeow/MihomoCoreManager.swift`
- `clash-meow/Sources/ClashMeow/CoreLogSupport.swift`
- `clash-meow/Sources/ClashMeow/MihomoAPI.swift`
- `clash-meow/Sources/ClashMeow/AppState.swift`
- `clash-meow/Sources/ClashMeow/RootView.swift`

日志路径：

```text
~/.config/clash-meow/runtime/mihomo/core.log
```

写入流程：

1. `MihomoCoreManager` 初始化时确定配置目录：

```text
~/.config/clash-meow/runtime/mihomo
```

2. `start()` 启动 mihomo：

```text
mihomo -d ~/.config/clash-meow/runtime/mihomo -f ~/.config/clash-meow/runtime/mihomo/config.yaml
```

3. 启动前打开 `core.log`：
   - 创建 `runtime/mihomo` 目录。
   - 如果不存在则创建 `core.log`。
   - seek 到文件末尾。
4. 写入一行 session header，记录启动时间、mihomo 路径和启动参数。
5. 将 mihomo 的 `standardOutput` 和 `standardError` 都接到同一个 `core.log`。
6. 进程退出、停止或启动失败时关闭文件句柄。

历史日志加载：

1. 日志页出现时执行 `state.loadLogs()`。
2. `loadLogs()` 调用 `CoreLogSupport.recentLogs(from: core.coreLogFile, limit: 500)`。
3. `CoreLogSupport` 读取 `core.log` 全文，取最后 500 行。
4. 对每行做简单级别推断：
   - 包含 `error` 为 `error`
   - 包含 `warn` 为 `warning`
   - 包含 `debug` 为 `debug`
   - 其他为 `info`

实时日志：

1. 用户点击日志页的“跟随”。
2. `state.startLogStream(level:)` 检查内核健康状态。
3. 根据当前筛选级别或运行配置里的 `logLevel` 生成 controller 日志级别。
4. `MihomoAPI.logStream(level:)` 打开 WebSocket：

```text
ws://<controller>/logs?level=<level>
```

5. 如果 controller secret 非空，会设置：

```text
Authorization: Bearer <secret>
```

6. WebSocket 收到文本后，`MihomoAPI.logEntry(from:)` 尝试按 JSON 解析：
   - `type` 或 `level` 作为日志级别。
   - `payload` 或 `message` 作为日志内容。
   - `time` 如果存在则保留。
7. 如果不是 JSON，就作为普通 info 日志展示。
8. `appendLog` 追加到 UI 内存数组，并保持最多 500 条。

UI 行为：

- 左侧“日志”页面展示日志。
- 顶部支持级别筛选。
- 支持搜索日志内容或级别。
- “跟随/暂停”控制 WebSocket 实时日志。
- “刷新”重新读取 `core.log` 最近 500 行。
- “清空”只清空 UI 内存里的 `state.logs`，不会删除 `core.log`。
- 右键单条日志可以复制消息，也可以复制当前可见日志。

## 第三方方案调研

### ClashX.Meta

ClashX.Meta 的“显示日志”不是直接请求 mihomo 的历史日志，而是打开应用自己维护的 CocoaLumberjack 日志文件。

相关代码：

- [ClashX.Meta/ClashX/Basic/Logger.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/9a9432aa82a7e92dac81d94c7ba02871b9d3c70e/ClashX/Basic/Logger.swift)
- [ClashX.Meta/ClashX/General/ApiRequest.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/9a9432aa82a7e92dac81d94c7ba02871b9d3c70e/ClashX/General/ApiRequest.swift)
- [ClashX.Meta/ClashX/AppDelegate.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/9a9432aa82a7e92dac81d94c7ba02871b9d3c70e/ClashX/AppDelegate.swift)

流程：

1. 应用启动时初始化 `Logger.shared`。
2. `Logger` 使用 `DDFileLogger` 写文件日志。
3. 日志文件每天滚动一次，最多保留 3 个文件。
4. DEBUG 构建还会把日志写到 `DDOSLogger`。
5. `ApiRequest` 维护一个 `/logs` WebSocket：
   - URL 为 `ConfigManager.apiUrl + "/logs?level=<selectLoggingApiLevel>"`。
   - 鉴权通过 `Authorization` header。
   - WebSocket 收到 mihomo 日志后，交给 `AppDelegate.didGetLog(log:level:)`。
6. `AppDelegate.didGetLog` 将内核日志再写入 `Logger`。
7. 用户点菜单“显示日志”时，`actionShowLog` 调用：

```swift
NSWorkspace.shared.openFile(Logger.shared.logFilePath())
```

也就是说，ClashX.Meta 的日志文件混合了两类内容：

- 应用自身事件，例如启动、代理设置、helper 安装、WebSocket 断线重连。
- 从 mihomo `/logs` WebSocket 收到的内核日志。

日志级别菜单会更新 `ConfigManager.selectLoggingApiLevel`，然后重置流式 API，使新的 `/logs?level=...` 生效。

### KumoApp

KumoApp 把日志分成运行时日志、运行事件、CLI debug 日志和其他组件日志，路径集中在：

```text
~/Library/Application Support/Kumo/logs
```

相关代码：

- [KumoApp/Sources/KumoCoreKit/Support/KumoPaths.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCoreKit/Support/KumoPaths.swift)
- [KumoApp/Sources/KumoCoreKit/Runtime/CoreSupervisor.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCoreKit/Runtime/CoreSupervisor.swift)
- [KumoApp/Sources/KumoCoreKit/KumoCoreKit.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCoreKit/KumoCoreKit.swift)
- [KumoApp/Sources/KumoCoreKit/Networking/MihomoControllerClient.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCoreKit/Networking/MihomoControllerClient.swift)
- [KumoApp/Sources/KumoCLIKit/Commands/LogCommands.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCLIKit/Commands/LogCommands.swift)
- [KumoApp/Sources/KumoCLIKit/Logging/DebugLogStore.swift](https://github.com/ProjectKumo/KumoApp/blob/990ff36dee2d3e40be1b4174a797bc255c34f685/Sources/KumoCLIKit/Logging/DebugLogStore.swift)

核心运行日志流程：

1. `KumoPaths` 定义日志目录和文件：
   - `logsDirectory`
   - `core.log`
   - `runtime-events.jsonl`
   - `kumo-service.log`
   - `substore.log`
   - `app-update-installer.log`
2. `CoreSupervisor.start` 启动 mihomo 进程。
3. 启动前调用 `paths.prepare()` 创建日志目录。
4. mihomo 的 `standardOutput` 和 `standardError` 都指向 `core.log`。
5. `logFileHandle()` 会创建 `core.log`，打开后 seek 到文件末尾，所以每次启动是追加写入。
6. core 生命周期事件另写入 `runtime-events.jsonl`，格式是 JSON Lines。
7. `KumoController.recentLogs(limit:)` 读取 `core.log` 末尾若干行，并根据文本推断日志级别。
8. `KumoController.logStream(level:)` 则通过 controller `/logs` WebSocket 获取实时日志。

CLI 查看日志：

```text
kumo logs runtime --limit 100 --level info
kumo logs cli --limit 20 --level notice
kumo logs path
kumo logs clean --dry-run
```

其中：

- `logs runtime` 读取 `core.log` 最近 N 行。
- `logs cli` 读取 `logs/cli/*-kumo-debug-*.log` 的摘要。
- `logs path` 输出日志目录。
- `logs clean` 清理旧 CLI debug/timing 文件。

CLI debug 日志会做简单脱敏，例如 bearer token、secret、URL 密码等会被替换为 `[redacted]`。

日志目录：

```text
app.getPath("userData")/logs
```

如果是 portable 模式，则使用：

```text
<exeDir>/data/logs
```

日志文件按日期命名：

```text
clash-party-YYYY-MM-DD.log
core-YYYY-MM-DD.log
sub-store-YYYY-MM-DD.log
```

应用日志流程：

1. `logger.ts` 创建按模块区分的 logger，例如 `Main`、`mihomo-core`、`mihomo-api`、`sysproxy`。
2. 所有模块 logger 都写入当天的 `clash-party-YYYY-MM-DD.log`。
3. 每行格式为：

```text
[ISO_TIME] [LEVEL] [MODULE] message
```

4. 同时也输出到 Electron main process 的 console。
5. 如果配置里 `disableAppLog` 为 true，则跳过 app 日志文件写入。

core 文件日志流程：

1. `manager.ts` 启动 mihomo core：

```text
spawn(corePath, ["-d", workDir, ctlParam, ipcPath])
```

2. 非 detached 模式下，创建两个 capped writable stream。
3. mihomo 的 stdout 和 stderr 都 pipe 到 `coreLogPath`。
4. `coreLogPath` 是一个函数，写入每个 chunk 时重新计算当天路径，所以跨日期后会自然写入新的 `core-YYYY-MM-DD.log`。
5. detached 模式使用 `stdio: "ignore"`，不会接管 stdout/stderr 写入 core 日志。

文件大小和清理策略：

1. `appendToFileWithLimit` 默认单文件上限为 10MB。
2. 配置项 `maxLogFileSize` 可以调整上限，最小 1MB。
3. 文件将超过上限时，不是简单停止写入，而是保留最近约 50% 内容，并插入：

```text
[LOG] File truncated because size limit reached.
```

4. `init.ts` 的 cleanup 会按 `maxLogDays` 清理过期日志，默认 7 天。
5. 清理依据是文件名里的 `YYYY-MM-DD`。

实时日志流程：

1. mihomo core ready 后，`manager.ts` 调用：

```text
startMihomoLogs()
```

2. `mihomoApi.ts` 读取受控配置里的 `log-level`，默认 `info`。
3. 主进程创建 WebSocket：

```text
ws://localhost/logs?level=<log-level>
```

4. 实际连接不走 TCP localhost，而是给 `ws` 传入自定义 `createConnection`，连接到 mihomo 的 IPC path。
5. 收到消息后尝试 `JSON.parse(data)` 为 `IMihomoLogInfo`。
6. 解析成功后通过 Electron IPC 发给 renderer：

```text
mainWindow.webContents.send("mihomoLogs", log)
```

7. WebSocket close/error 后会按 stream 状态自动重连，重试次数为 10，间隔 1 秒。

Renderer 日志页：

1. `preload/index.ts` 只允许白名单 channel，其中包含 `mihomoLogs`。
2. `logs.tsx` 在模块加载时注册：

```text
window.electron.ipcRenderer.on("mihomoLogs", ...)
```

3. 收到日志后补一个本地 `time = new Date().toLocaleString()`。
4. 日志只缓存在 renderer 内存里的 `cachedLogs.log`。
5. 最多保留 500 条；超过后丢弃最早一条。
6. 页面支持搜索，搜索范围是 `payload` 和 `type`。
7. 支持自动滚动开关。
8. 清空按钮只清空 renderer 内存缓存，不删除任何日志文件。
9. 列表用 `react-virtuoso` 虚拟滚动渲染。
10. 单条日志用卡片展示，按 `error`、`warning`、`info`、`debug` 映射颜色。

与 clash-meow 的主要差异：

- clash-party 日志页不主动读取 `core-YYYY-MM-DD.log` 历史文件，只显示当前应用运行期间通过 IPC 收到的实时日志。
- clash-party 的 core 文件日志来自进程 stdout/stderr，实时 UI 日志来自 mihomo `/logs` WebSocket，两者并行存在。
- clash-party 有内置按日期命名、按大小截断、按天数清理的日志治理。
- clash-party 的 WebSocket 通过 IPC socket/named pipe 连接 controller，而不是直接拼 controller host/port。

## 方案对照

| 项目 | 历史日志来源 | 实时日志来源 | 查看方式 | 文件策略 |
| --- | --- | --- | --- | --- |
| ClashX.Meta | CocoaLumberjack 文件 | `/logs` WebSocket 写入文件 | 打开当前日志文件 | 每天滚动，最多 3 个文件 |
| KumoApp | `core.log` | `/logs` WebSocket | CLI/API 读取或 App 内消费 | 组件分文件，CLI debug 可清理 |
| clash-meow | `~/.config/clash-meow/runtime/mihomo/core.log` | `/logs` WebSocket | App 内日志页 | 追加写入，UI 最多保留 500 条 |
| clash-party | UI 不读历史文件；文件侧有 `core-YYYY-MM-DD.log` | 主进程 `/logs` WebSocket 后 IPC 到 renderer | App 内实时日志页 | 按日期分文件，大小截断，按天数清理 |

## 第三方调研带来的启发

当前 clash-meow 已经覆盖了核心查看链路：历史文件、实时跟随、级别筛选、搜索和复制。推荐方案主要吸收了以下第三方经验：

1. 增加“在 Finder 中显示日志文件”或“打开日志文件”按钮。
2. 增加日志滚动策略，避免 `core.log` 无限增长。
3. 把应用自身日志和 mihomo 内核日志区分存储，例如 `app.log` 与 `core.log`。
4. “清空”可以提供两个动作：只清空当前视图、截断/删除日志文件。
5. 记录结构化运行事件，例如启动、停止、端口释放、helper 调用，方便排查非内核问题。
6. 参考 clash-party 增加单文件大小上限和保留最近内容的截断策略。
7. 参考 clash-party 增加日志保留天数配置，启动时清理过期日志。
