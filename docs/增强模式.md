# 增强模式

本文记录 Clash Meow 对增强模式（TUN）的推荐处理方式，并对比 ClashX.Meta、KumoApp、clash-party 三个开源项目在开启和关闭 TUN 时的实现。

## Clash Meow 推荐方案

增强模式开关采用“单飞操作 + 修改受控配置 + mihomo API reload + 运行时校验 + 必要时特权 restart fallback + 失败回滚”的流程。开启和关闭走同一套状态机，区别只在目标值为 `true` 或 `false`。

1. 用户点击增强模式开关时，如果已有一次增强模式应用正在进行，拒绝新的点击，恢复按钮显示，并提示用户稍后再试。
2. 开启增强模式前，必须确认 mihomo 内核已启动；未启动时不允许开启，提示用户，并恢复按钮和持久化状态。关闭增强模式在停止内核流程中可以只落本地状态，不要求 restart。
3. UI 进入“应用中”状态，禁用增强模式开关，避免连续点击造成多次 reload/restart 互相覆盖。
4. 保存操作前状态：
   - 当前按钮状态。
   - `tunEnabled`。
   - `tunUserEnabled`。
   - 修改前的 `config.yaml`。
5. 通过 `RuntimeConfigBuilder` / `Yams` 结构化修改 `~/.config/clash-meow/runtime/mihomo/config.yaml` 中的 `tun.enable`，避免按字符串写入破坏 YAML 结构。
6. 优先调用 mihomo controller `PUT /configs?force=true` reload 当前 runtime config。
7. reload 成功后，再调用 `GET /configs` 校验运行时 `tun.enable` 是否等于目标值。
8. 只有 reload 成功且运行时校验一致，才写入：
   - `tunEnabled`
   - `tunUserEnabled`
9. 如果 API reload 不可用、失败、超时或校验不一致，fallback 到 restart：
   - 通过 `com.clash.meow.helper` 停止并重新以 root 启动 mihomo。
   - 最多等待 12 秒，直到 controller `/version` 可访问。
   - controller ready 后再调用 `GET /configs` 校验 `tun.enable`。
   - 只有校验一致才认为本次操作成功。
10. 如果 reload 和 restart fallback 都失败：
   - 写回修改前的 runtime config。
   - 恢复按钮状态。
   - 恢复 `tunEnabled` / `tunUserEnabled`。
   - 如果 core 仍可恢复，则按回滚后的 runtime config 再启动/重启一次。
   - 提示用户 TUN 设置失败。

启动恢复也遵循同样的规则：

1. App 启动后如果需要自动启动 core，通过 privileged helper 以 root 启动 mihomo。
2. 启动后最多等待 12 秒，直到 controller `/version` 可访问；这段时间不要把 `127.0.0.1:9090` 的连接失败当作核心失败。
3. controller ready 后再读取配置、恢复系统代理、恢复用户意图里的增强模式。
4. 如果增强模式恢复失败，保持 `tunUserEnabled` 作为用户意图，但 `tunEnabled` 和 UI 只表示最后一次成功应用的实际状态。

旧版流程的问题有两类。第一类是把进程启动成功等同于 controller 可用；开启 TUN 时 mihomo 需要创建 `utun`、设置路由和 DNS hijack，controller 端口可能晚几秒才监听，如果此时立刻请求 `/configs` 并把 connection refused 当作失败，就会触发反复 restart，表现为核心开关自动来回切换。第二类是普通用户进程没有权限配置 TUN，mihomo 日志会出现 `Start TUN listening error: configure tun interface: Connect: operation not permitted`，因此 App bundle 下 core 生命周期统一由 privileged helper 托管。

文件监听需要配合 TUN 应用流程：

1. App 自己生成或结构化写入 `config.yaml` 后，会短时间抑制文件变更通知，避免把自己的写入误判成外部修改。
2. 只要增强模式仍处于应用中，也继续抑制文件变更通知；授权弹窗、helper 安装或 restart 可能超过普通抑制窗口。
3. 这样可以避免应用中的 YAML 写入被外部变更处理抢先 reload，导致 UI 偏好已是开启但 `config.yaml` 又被重载回关闭。

理由：

1. `PATCH /configs` 只适合少数运行时 basic config，例如 `mode`、`log-level`、端口等；TUN 牵涉虚拟网卡、路由、DNS hijack，不应只把 patch 请求成功当作 TUN 真正成功。
2. `PUT /configs?force=true` 是 mihomo 官方用于 reload 配置文件的 API，比直接关闭并重新启动进程更平滑。
3. macOS 上 TUN 的启动权限取决于 mihomo 进程权限；Clash Meow 的 App bundle 运行时始终由 privileged helper 以 root 启动 core。
4. TUN 是否可用最终取决于 mihomo 运行时是否成功加载新配置，因此必须 reload 或 restart 后再读运行时状态确认。
5. 用户操作和最后一次正确实际状态要分开持久化；失败或不允许开启时，持久化值必须恢复到修改前。

## ClashX.Meta

结论：ClashX.Meta 的 `origin/meta` 分支有可验证的 TUN 开关实现。它开启和关闭 TUN 时不 stop/start mihomo，而是通过 mihomo controller `PATCH /configs` 修改运行时 `tun.enable`，再同步配置并通过 privileged helper 更新系统 DNS hijack 状态。

UI / 快捷方式流程：

1. 菜单点击 `AppDelegate.actionSetTunMode(_:)`。
2. 快捷键会调用同一个 `AppDelegate.shared.actionSetTunMode(nil)`。
3. AppleScript `TunMode` 命令也会取 `delegate.tunModeMenuItem` 后调用 `delegate.actionSetTunMode(menuItem)`。
4. `actionSetTunMode` 会根据菜单项当前状态计算目标值，并临时禁用菜单项。
5. 如果 SSID suspend 规则不允许本次操作，则恢复菜单项可用状态并返回。
6. 允许操作时调用 `SystemProxyManager.shared.toggleTunMode(enabled:)`。

核心流程：

1. `SystemProxyManager.toggleTunMode(enabled:persistent:)`：
   - 开启且需要持久化时，先检查 SSID suspend。
   - 调 `ConfigReloadManager.shared.setTunMode(enabled:)`。
   - 如果 `persistent == true`，把 `ConfigManager.shared.proxyState.isTunModeEnabled` 写为目标值。
2. `ConfigReloadManager.setTunMode(enabled:)`：
   - 调 `ApiRequest.updateTun(enable:)`。
   - 调 `syncConfigWithTun()`。
3. `ApiRequest.updateTun(enable:)`：
   - 向 `/configs` 发 `PATCH`。
   - body 是 `{"tun": {"enable": enabled}}`。
   - 请求失败只写日志 `update tun failed`，没有向上抛出失败。
4. `syncConfigWithTun()`：
   - 先 `GET /configs` 同步当前运行配置。
   - 从 `config.tun.enable` 读取实际状态。
   - 调 privileged helper 的 `ProxyConfigHelperMessages.UpdateTun(state:dns:)`。
5. helper 收到 `UpdateTun` 后：
   - `metaDNS.setCustomDNS(message.dns)`。
   - TUN 开启时 `metaDNS.hijackDNS()`。
   - TUN 关闭时 `metaDNS.revertDNS()`。
   - 最后 `flushDnsCache()`。

配置切换时：

1. `ConfigReloadManager.updateConfig` 会先 `startProxyCore()` 确保 core 已启动。
2. 然后通过 `requestConfigUpdate(configPath:)` reload 配置：
   - controller 模式：`PUT /configs`，body 为 `{"Path": configPath}`。
   - internal API 模式：`clashUpdateConfig(configPath)`。
3. reload 成功后调用 `syncConfigWithTun()`，按新配置里的 `tun.enable` 同步 helper 的 DNS hijack 状态。
4. 如果用户持久化意图 `isTunModeEnabled` 为 true，配置更新回调里会再次 `toggleTunMode(enabled: true, persistent: false)`，把 TUN 打回开启。

退出和持久化：

1. `ConfigManager.ProxyState.isTunModeEnabled` 初始值来自 UserDefaults key `restoreTunProxy`。
2. `ConfigManager.currentConfig` 更新时，会把 `proxyState.isTunModeActive` 同步为运行时 `config.tun.enable`。
3. 退出时 `ExitManager` 会把 `isTunModeEnabled` 写为当前实际 `isTunModeActive`。
4. 这意味着 ClashX.Meta 更接近“下次启动恢复退出时实际 TUN 状态”，不是 Clash Meow 当前设计里的“用户意图”和“最后正确实际状态”分开保存。

ClashX.Meta 的关键点：

1. TUN 开关不是 stop/start mihomo。
2. TUN 开关使用 `PATCH /configs` 更新 `tun.enable`。
3. 开关后会 `GET /configs` 读取实际运行状态。
4. privileged helper 不负责启动 TUN 本身，而是根据运行时 TUN 状态处理 DNS hijack/revert 和 DNS cache flush。
5. 失败处理偏弱：`ApiRequest.updateTun` 捕获错误后只记录日志，`setTunMode` 仍会继续 `syncConfigWithTun()`；如果 PATCH 失败，最终 helper 会按 `GET /configs` 读到的旧状态同步。

## KumoApp

结论：KumoApp 开启和关闭 TUN 时会更新自己的 runtime settings；如果 core 正在运行，则 restart mihomo，并等待 controller ready。

UI 流程：

1. `TunView` 的 `Enable TUN` 开关绑定到 `store.setTunEnabled(isEnabled)`。
2. `KumoAppStore.setTunEnabled(_:)` 调用 `controller.setTunEnabled(isEnabled)`。
3. 调用成功后刷新 core status、service status、TUN status。
4. 如果 core 正在运行，等待 controller ready 后重新加载 core configuration。

核心流程：

1. `KumoController.setTunEnabled(_:)` 先检查是否存在 running service client；有 privileged service 时，转发到 service 的 `/tun/enable` 或 `/tun/disable`。
2. 没有 service client 时，读取本地 state。
3. 开启 TUN 且当前进程或 helper 不能管理 TUN 时：
   - 记录 `TunStatus(isEnabled: false, isRunning: false, requiresService: true, lastError: ...)`。
   - 保存 state。
   - 抛出 `serviceUnavailable`。
4. 能管理 TUN 时，更新 `runtimeSettings.tun.isEnabled` 并保存 state。
5. 如果 core 当前是 running，则调用 `restart()`，然后 `waitForControllerReady()`。
6. 最后返回 `tunStatus()`。

配置生成：

1. KumoApp 不直接修改用户 profile YAML。
2. `RuntimeConfigBuilder` 会生成 Kumo 受控的 runtime config。
3. 只有 `runtimeSettings.tun?.isEnabled == true` 时，才写入 `tun:` section。
4. 写入内容包含 `enable: true`、`stack`、`auto-route`、`auto-redirect`、`auto-detect-interface`、`strict-route`、DNS hijack、route exclude、MTU、device 等。
5. 关闭 TUN 时，runtime config 不写入受控 TUN section。

KumoApp 的关键点：

1. TUN 需要 privileged helper 或 privileged process。
2. TUN 开关不是 `PATCH /configs`。
3. core 运行中开启或关闭 TUN 会 restart core。
4. helper service 模式下，TUN 操作通过本地 service API 执行，但 service 内部仍然调用同一套 controller 逻辑。

## clash-party

结论：clash-party 的 TUN 开关会修改受控配置 `mihomo.yaml`，生成 runtime config，并尝试通过 mihomo API 热更新。TUN 设置页显式保存时会调用 `PUT /configs?force=true` hot reload；托盘和快捷键路径会调用 `PATCH /configs` 尝试热 patch，但失败只记录警告，最终变化至少会在下一次 reload/restart 生效。

受控配置：

1. 默认 TUN 配置定义在 `DEFAULT_MIHOMO_TUN_CONFIG`，默认 `enable: false`。
2. 受控配置文件由 `getControledMihomoConfig()` 读取或创建。
3. `patchControledMihomoConfig(patch)` 会 deep merge patch，写回受控配置，并调用 `generateProfile()` 生成 mihomo runtime config。
4. 生成 runtime config 时，会把当前 profile 与受控 mihomo config 合并；受控配置里的 `tun` 覆盖 profile 中对应字段。
5. 如果没有接管 DNS 且最终 DNS 未启用，会清空 `tun.dns-hijack`，避免 DNS 流量被劫持后无人处理。

TUN 页面流程：

1. `pages/tun.tsx` 读取 `controledMihomoConfig.tun`。
2. 保存 TUN 参数时调用 `patchControledMihomoConfig({ tun: ... })`。
3. 随后调用 `mihomoHotReloadConfig()`。
4. `mihomoHotReloadConfig()` 会：
   - 调 `generateProfile()`。
   - 计算当前 work config 路径。
   - 调 mihomo controller `PUT /configs?force=true`，body 为 `{ path: configPath }`。

托盘和快捷键流程：

1. 托盘菜单和快捷键读取 `getControledMihomoConfig().tun?.enable`。
2. 开启时 patch `{ tun: { enable: true }, dns: { enable: true } }`；关闭时 patch `{ tun: { enable: false } }`。
3. `patchControledMihomoConfig()` 内部会尝试 `patchMihomoConfig(patch)`。
4. `patchMihomoConfig()` 调用 mihomo controller `PATCH /configs`。
5. 如果 hot patch 失败，只记录 warning，提示“changes will apply on next restart”。

权限处理：

1. 非 Windows 平台的 TUN 页面提供 `grantTunPermissions()`，成功后会 `restartCore()`。
2. Windows 平台提供 firewall setup，成功后也会 `restartCore()`。
3. 托盘开启 TUN 前也会检查或请求 TUN 权限；失败时会恢复菜单项 checked 状态并返回。

clash-party 的关键点：

1. TUN 状态存放在 App 受控的 mihomo config 中，不直接让订阅 profile 决定。
2. 显式 TUN 设置页使用 `PUT /configs?force=true` reload，不主动 stop/start。
3. 托盘和快捷键路径更轻量，先尝试 `PATCH /configs`，失败后等待下次 restart 生效。
4. 权限相关操作成功后会 restart core。

## 对比

| 项目 | TUN 开关源码是否可见 | 是否直接 `PATCH /configs` | 是否 `PUT /configs?force=true` reload | 是否 restart core | 权限策略 | 失败处理特点 |
| --- | --- | --- | --- | --- | --- | --- |
| ClashX.Meta | 可见 | TUN 开关使用 `PATCH /configs` | 配置切换使用 reload | TUN 开关不主动 restart | helper 处理 DNS hijack/revert | PATCH 失败只记录日志，随后按 `GET /configs` 读到的实际状态同步 helper |
| KumoApp | 可见 | 否 | 否 | core running 时 restart | 需要 privileged helper 或 privileged process | 无权限时记录失败状态并抛错 |
| clash-party | 可见 | 托盘/快捷键会尝试 | TUN 设置页会 reload | 权限操作会 restart；设置页不主动 restart | 非 Windows 平台显式授予 TUN 权限 | patch 失败仅 warning，reload 失败由 UI catch |

## 对 Clash Meow 的取舍

Clash Meow 更适合采用 clash-party 的受控配置和 hot reload 思路，并结合 KumoApp 的 privileged process 判断，同时补上比 clash-party 更严格的状态校验与回滚：

1. 可以参考 ClashX.Meta 的“`PATCH /configs` 后立刻 `GET /configs` 同步实际状态”的验证意识，但不能照搬它的失败处理；Clash Meow 需要把失败明确返回给 UI 并回滚持久化。
2. 不完全采用 KumoApp 的 restart-only 模型，因为 mihomo 已提供 `PUT /configs?force=true` reload，可以减少进程 stop/start。
3. 采用 clash-party 的“受控 runtime config + `PUT /configs?force=true`”作为优先路径。
4. 比 ClashX.Meta 和 clash-party 更严格：reload 或 patch 后必须 `GET /configs` 校验 `tun.enable`；失败必须回滚 YAML、按钮和持久化状态。
5. 保留 restart fallback，用于 API reload 不支持、失败或运行时校验不一致的场景。
6. restart fallback 和启动恢复都通过 `com.clash.meow.helper` 以 root 启动 mihomo；关闭 TUN 后仍可继续使用当前运行的 root core，并以运行时校验结果为准。
