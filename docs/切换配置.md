# dou-clash 切换配置方案

本文先记录 `dou-clash` 当前采用的切换配置方案，再记录 `ClashX.Meta`、`KumoApp`、`Clash Party / Mihomo Party` 三个第三方应用在“切换配置 / Profile”时实际做了什么，作为设计依据。

## 当前方案

当前采用 Clash Party 的折中模型，并以 KumoApp 的受控运行时配置思路作为主线：

- Profile 不是最终运行配置，只是输入。
- `dou-clash` 每次切换 Profile 时，都通过 `RuntimeConfigBuilder` 和 `Yams` 生成一份 App 受控的 runtime config。
- 默认策略是关闭当前 mihomo，再用新 runtime config 启动 mihomo。
- 切换失败时必须回滚 current profile，避免 UI、持久化状态和实际运行的 core 状态不一致。
- 热重载不作为首版默认路径；后续可以作为高级优化开关加入。

### 具体步骤

1. 用户选择目标 Profile。
2. 记录当前运行状态：
   - `oldProfileID`
   - core 是否正在运行
   - 当前 runtime config 路径
   - 当前 controller readiness / dashboard 状态
3. 先不要立即提交 `currentProfileID`。
4. 使用目标 Profile 生成新的 runtime config：
   - 读取目标 Profile 原始 YAML。
   - 用 `Yams` 解析成结构化 mapping。
   - 移除 `dou-clash` 控制的 runtime key。
   - 追加 `dou-clash` 控制的 runtime key。
   - 输出到 App 管理的运行时配置路径。
5. runtime config 中由 App 强制控制这些关键字段：
   - `external-controller`
   - `secret`
   - `mixed-port` / `port` / `socks-port`
   - `mode`
   - `allow-lan`
   - `log-level`
   - `find-process-mode`（固定为 `always`）
   - TUN 配置
   - DNS 配置和 Sniffer 配置已预留为受控 key，后续 UI 接管时继续由 builder 生成。
   - 其他和系统代理、dashboard、App 状态联动的字段。
6. 对新 runtime config 做启动前校验：
   - YAML 能解析。
   - 至少包含有效的代理或 provider。
   - mihomo 可以通过配置检查。
   - controller 参数没有被订阅覆盖；`mixed-port` 在没有 App 显式端口偏好时继承 Profile。
   - App 侧展示用的轻量解析必须容忍订阅里的复杂 YAML 结构，不能因为嵌套数组、重复节点名或重复订阅头字段导致 UI 崩溃。
7. 如果 core 当前没有运行：
   - 只提交 `currentProfileID = newProfileID`。
   - 保存生成好的 runtime config。
   - 不自动启动 mihomo。
8. 如果 core 当前正在运行：
   - 停止当前 mihomo。
   - 清理 pid、controller 连接、日志/流量 stream、旧 readiness 状态。
   - 使用新 runtime config 启动 mihomo。
   - 等待 controller ready。
9. controller ready 后：
   - 提交 `currentProfileID = newProfileID`。
   - 写入 `preferences.json.mihomoSettings.selectedProfileID = newProfileID`，作为当前 Profile 的唯一持久化状态。
   - 刷新 dashboard。
   - 重新读取 proxies / proxy-groups / rules / providers。
   - 重启 traffic / log / connection stream。
   - 如有系统代理开启，确认它仍指向当前 App 控制的端口。
10. 如果任何一步失败：
   - 不提交新 `currentProfileID`，或把它回滚到 `oldProfileID`。
   - 不更新 `mihomoSettings.selectedProfileID`。
   - 如果旧 core 仍可用，保留旧 core 状态。
   - 如果旧 core 已经被停止，尝试用旧 profile 重新生成 runtime config 并恢复启动。
   - 向 UI 返回明确错误。

推荐流程可以概括为：

```text
用户选择 Profile
  -> 记录 oldProfileID
  -> 生成目标 Profile 的受控 runtime config
  -> 校验 runtime config
  -> core 未运行：提交 currentProfileID，结束
  -> core 运行中：stop mihomo
  -> start mihomo with new runtime config
  -> wait controller ready
  -> 提交 currentProfileID
  -> 刷新 dashboard / proxies / streams
  -> 失败则回滚 currentProfileID，并尽量恢复旧 runtime
```

### 为什么这样设计

不要让用户订阅 YAML 直接成为运行时真相。运行时真相应该由 `dou-clash` 生成。

这样做的主要理由：

1. **控制权稳定**：controller、secret、mode、TUN、DNS、Sniffer 等字段和 App 行为强相关，应该由 App 统一控制；`mixed-port` 默认继承 Profile，避免用户修改 YAML 后启动端口仍停在旧默认值。
2. **订阅不可控**：第三方订阅 YAML 可能包含端口、DNS、TUN、controller 等字段，直接 reload 会让 App 设置被覆盖。
3. **状态更一致**：先生成、校验、启动成功后再提交 current profile，比“先切过去，失败后用户自己处理”更可靠。
4. **失败可恢复**：借鉴 Clash Party，切换失败要回滚 current profile；必要时恢复旧 runtime。
5. **实现更可维护**：所有配置切换都经过同一个 `RuntimeConfigBuilder`，后续加 override、DNS、TUN、系统代理联动时不会散在多条路径里。
6. **重启成本可接受**：切换 Profile 是低频操作。相比毫秒级热重载，稳定性和可解释性更重要。

### 解析容错

`dou-clash` 的运行时真相以 mihomo 解析结果为准；App 自己解析 Profile 只用于导入校验、概览展示和离线节点预览。因此 App 侧解析必须采取容错策略：

1. 只解析 `proxies:` 顶层一级代理条目，不能把代理内部的 `alpn`、`headers` 等嵌套数组误识别为代理节点。
2. 如果订阅出现同名代理节点，UI 预览索引使用最后一次出现的节点信息，避免 `Dictionary(uniqueKeysWithValues:)` 这类唯一键假设导致进程崩溃。
3. 如果服务端返回重复订阅用量字段，后出现的字段覆盖先出现的字段。
4. 这些容错只影响 App 展示和元数据提取；最终配置是否能运行仍交给 mihomo 启动和 reload 校验决定。

### 关于热重载

热重载可以保留为后续优化，但不建议作为首版主路径。

如果后续实现热重载，推荐采用 Clash Party 的方式：

1. 仍然先生成 App 受控 runtime config。
2. 校验成功后调用 Mihomo controller：
   - `PUT /configs?force=true`
   - body 传生成后的 runtime config 路径。
3. 热重载成功后刷新 proxies / rules / providers。
4. 可选关闭所有连接。
5. 热重载失败时 fallback 到默认 restart 流程。

也就是说，即使加入热重载，也不要退回 ClashX.Meta 那种“把用户原始 YAML 路径直接交给 core”的模型。

## 第三方应用调研

## ClashX.Meta

ClashX.Meta 的配置单位是 `~/.config/clash/*.yaml` 文件名。菜单里显示的是去掉 `.yaml` 后缀的配置名，当前配置名保存在 `UserDefaults.selectConfigName`。

### 入口

- 菜单项由 `MenuItemFactory.generateSwitchConfigMenuItems` 生成。
- 本地模式下读取 `~/.config/clash/` 里所有 `.yaml` 文件。
- iCloud 模式下从 iCloud 配置目录读取列表。
- 菜单项选中态由 `ConfigManager.selectConfigName == config` 决定。
- 如果外部控制器已经指定了 `RemoteControlManager.selectConfig`，切换菜单会被隐藏。

### 选择配置后

用户点菜单后会进入 `AppDelegate.updateConfig(configName:)`。核心步骤如下：

1. 调用 `startProxy()`，确保 Clash core 已经启动。
2. 如果 core 没有 running，直接返回。
3. 计算目标配置文件路径：
   - 本地：`~/.config/clash/<configName>.yaml`
   - iCloud：`<iCloud config dir>/<configName>.yaml`
4. 清理 `ClashProxy` 缓存。
5. 调用 `ApiRequest.requestConfigUpdate(configName:)` 应用配置。

### 应用到 core

`ApiRequest.requestConfigUpdate(configPath:)` 有两条路径：

- 内置 API 模式：调用 Go 导出的 `clashUpdateConfig(path)`。
  - Go 侧执行 `executor.ParseWithPath(path)` 解析目标 YAML。
  - 解析成功后执行 `executor.ApplyConfig(cfg, false)`。
  - 返回 `"success"` 表示切换成功，否则返回错误信息。
- 外部 controller/API 模式：向 Mihomo/Clash controller 发 `PUT /configs`，JSON body 为 `{"Path": configPath}`。
  - HTTP 204 视为成功。
  - 非 204 时读取返回 JSON 的 `message` 作为错误。

也就是说，ClashX.Meta 不重新生成一份运行时配置文件，而是把目标 YAML 路径交给 core/controller 做 reload。

这里没有主动关闭 mihomo 进程再重新启动。切换配置是一次 core 内部的配置 reload：进程保持运行，配置对象被重新解析并应用。

### 成功后的收尾

配置 reload 成功后，`AppDelegate.updateConfig` 会继续做这些事情：

1. `syncConfig()`：重新读取 `/configs`，更新 `ConfigManager.shared.currentConfig`。
2. `resetStreamApi()`：重置日志和流量 WebSocket。
3. 执行一次性的 `runAfterConfigReload` 回调。
4. 发出“Reload Config Succeed”通知。
5. 如果本次传入了新的 `configName`，写入 `ConfigManager.selectConfigName`。
   - 写入时会调用 `ConfigManager.watchCurrentConfigFile()`。
   - 这会把文件监听切到当前配置文件。
6. `selectProxyGroupWithMemory()`：按当前配置名恢复之前记住的代理组选择。
   - 记忆结构是 `SavedProxyModel(group, selected, config)`。
   - 只恢复 `item.config == ConfigManager.selectConfigName` 的记录。
   - 恢复失败的记录会被移除。
7. `selectOutBoundModeWithMenory()`：恢复全局出站模式。
   - 调 `PATCH /configs` 或内部 API 更新 `mode`。
   - 成功后关闭所有连接并再次同步配置。
8. 重建代理菜单。
9. 通知 dashboard reload。

### 失败时

- 展示 “Reload Config Fail” 通知。
- 不更新 `selectConfigName`。
- 不切换文件监听。
- 不恢复代理组/出站模式。

## KumoApp

KumoApp 的配置单位是 Profile ID，而不是裸 YAML 文件名。Profile 文件、当前选择和元数据都放在 Application Support 目录下。

主要文件：

- `profiles/<id>.yaml`：Profile 原始 YAML。
- `profiles/current.txt`：当前 Profile ID。
- `profiles/profiles-metadata.json`：Profile 名称、来源、远程 URL、更新时间、自动更新等元数据。
- `work/config.yaml`：实际启动 Mihomo 时使用的运行时配置文件。
- `state.json`：core 状态、controller endpoint、端口、mode、runtime settings、系统代理状态等。

### 入口

切换入口主要有两个：

- SwiftUI Profiles 页面调用 `KumoAppStore.selectProfile(_:)`。
- 菜单栏 Profiles 子菜单调用同一个 store 方法。

菜单栏里只展示前 8 个 profile：

- 当前 profile 显示选中态。
- 当前 profile 和 loading 状态下不可点。

Spotlight / AppIntents 也会通过 profile id 找到目标 profile，再调用同一套选择逻辑。

### 选择 Profile 后

`KumoAppStore.selectProfile(_:)` 的步骤是：

1. 调用 `controller.setCurrentProfile(id:)`。
2. `ProfileRepository.setCurrentProfile(id:)` 把 id 原子写入 `profiles/current.txt`。
   - 这是 KumoApp 的状态文件；DouClash 不采用该文件，而是只使用 `preferences.json.mihomoSettings.selectedProfileID`。
3. `refreshProfiles()` 重新读取 profile 列表和当前 profile。
4. 如果 core 当前是 running：
   - 调 `controller.restart()`。
   - 等待 controller ready。
   - 重启流量流。
   - 重新加载代理组。
   - 重新读取 core configuration。
5. 如果 core 当前没有 running：
   - 只持久化当前 profile。
   - 不启动 core。
   - 下次 `start()` 时才会加载新的当前 profile。

### restart / start 做了什么

`KumoController.restart()` 在非 service backend 路径下等价于：

1. `stop()`：停止当前 Mihomo 进程，清理 PID 和状态。
2. `start()`：重新启动。

所以 KumoApp 在 core 已运行时切换 Profile，当前实现是关闭当前 mihomo，再用新生成的运行时配置启动 mihomo。它不是像 ClashX.Meta 那样调用 controller 的 `/configs` reload 指定 YAML。

`KumoController.start()` 会：

1. 读取当前状态 `state.json`，拿到 endpoint、端口、mode、runtime settings 等。
2. 调 `ProfileRepository.loadDefaultProfile()`，它会读取 `profiles/current.txt` 指向的 `<id>.yaml`。
3. 读取所有 active overrides。
4. 构造 `CoreLaunchConfiguration`。
5. 交给 `CoreSupervisor.start(configuration:)`。

`CoreSupervisor.start` 里真正生成并启动运行时配置：

1. `paths.prepare()` 准备目录。
2. 检查记录的 PID 是否仍然存活，避免重复启动。
3. 解析 core 可执行文件路径。
4. 用 `RuntimeConfigBuilder.write(...)` 写出 `work/config.yaml`。
5. 启动 mihomo 进程，参数是：
   - `-d <workDirectory>`
   - `-ext-ctl <host>:<port>`
   - 如有 secret，再追加 `-secret <secret>`
6. 写入 `core.pid`。
7. 保存新的 `CoreStatus` 到 `state.json`。
8. 追加 runtime event。

### RuntimeConfigBuilder 做了什么

KumoApp 不直接把 profile YAML 原样交给 mihomo。它会生成一份受控运行时配置：

1. 先把 profile 原始 YAML 解析成结构化 YAML。
2. 依次合并 active overrides。
3. 移除 Kumo 自己控制的顶层 key，例如：
   - `external-controller`
   - `secret`
   - `port`
   - `socks-port`
   - `mixed-port`
   - `mode`
   - `allow-lan`
   - `log-level`
   - `ipv6`
   - `tun`
   - `dns`
   - `sniffer`
   - `hosts`
4. 在文件末尾追加 `# Kumo controlled runtime settings`。
5. 写入 Kumo 控制的 controller、端口、mode、allow-lan、log-level、geo、TUN、DNS、Sniffer、hosts 等配置。

DouClash 对端口采用更贴近当前产品形态的策略：`RuntimeConfigBuilder` 会生成受控 runtime config，但 `mixed-port` 默认继承 Profile；只有未来偏好设置提供明确端口值时，才由 App 覆盖。

这意味着 Profile 切换时，profile 里的节点、规则、proxy-groups 等会变化，但 Kumo 控制的 runtime key 会保持来自 UI / state 的值，避免被订阅 YAML 覆盖。

### service backend 路径

如果 privileged service 正在运行，`start()` / `stop()` / `restart()` 会通过 `KumoServiceClient` 发请求给 helper：

- `POST /core/start`
- `POST /core/stop`
- `POST /core/restart`

App 侧仍然先写 `current.txt`。真正的启动/重启动作由 service 执行。这个路径保留了同样的 profile/current-state 语义，只是执行进程从 App 内 supervisor 变成 helper。

helper 收到 `POST /core/restart` 后会创建 `KumoController(paths: paths, useServiceBackend: false)` 并调用同一个 `restart()`。因此 service backend 下也仍然是 stop/start，只是 stop/start 发生在 privileged service 进程里。

### 成功后的收尾

Profile 切换并重启成功后，UI store 会：

- 等待 Mihomo controller ready。
- 重新开启 traffic stream。
- 重新加载代理组。
- 重新读取 core configuration。
- 刷新 profile 列表和 current profile。

KumoApp 当前没有像 ClashX.Meta 那样按 profile 维度恢复每个代理组的上次选择。代理组选择是通过当前运行的 Mihomo controller 操作，不在切换 profile 后做 per-profile memory replay。

## Clash Party / Mihomo Party

Clash Party 是 Electron + React 应用，配置单位也是 Profile。它和 KumoApp 一样会生成运行时配置，但切换 Profile 时有两种可配置策略：

- 默认策略：关闭当前 mihomo，再重新生成配置并启动 mihomo。
- 可选策略：热重载 Profile，重新生成配置后调用 Mihomo controller 的 `/configs?force=true`。

默认配置里 `useHotReloadProfile: false`，所以默认行为是重启 core；只有用户打开热重载开关后才会走 reload。

### 入口

主要入口在 Profiles 页面：

- `src/renderer/src/pages/profiles.tsx` 渲染每个 `ProfileItem`。
- 点击 Profile 时调用 `changeCurrentProfile(item.id)`。
- `useProfileConfig` 先做乐观更新：把前端 SWR cache 里的 `current` 改成目标 id，并发送 `updateTrayMenu`。
- 然后通过 IPC 调 main 进程的 `changeCurrentProfile(id)`。

`useProfileConfig` 还做了一层前端串行化：

- `targetProfileId` 记录最后一次点击的目标 Profile。
- `pendingTask` 避免并发切换。
- 如果切换失败，会弹出 `switchProfileFailed` 错误并重新 mutate。

### 当前 Profile 存在哪里

Clash Party 的 Profile 总表是 `profile.yaml`：

- 路径由 `profileConfigPath()` 返回，即 `dataDir()/profile.yaml`。
- 结构是 `IProfileConfig`，包含 `current` 和 `items`。
- 每个 Profile 的 YAML 内容放在 `profiles/<id>.yaml`。
- 如果没有指定 id 或文件不存在，会使用内置 `defaultProfile`。

main 进程通过 `getProfileConfig(true)` 读取最新文件，再通过 `updateProfileConfig` 串行写回。

### 切换 Profile 后

main 进程入口是 `src/main/config/profile.ts` 的 `changeCurrentProfile(id)`。核心流程：

1. 使用 `changeProfileQueue` 串行化切换，避免多个切换任务并发。
2. 读取旧的 `current`。
3. 如果旧值已经等于目标 id，直接返回。
4. 先写 `profile.yaml`，把 `config.current` 改成目标 id。
5. 读取 app config：
   - `useHotReloadProfile`
   - `hotReloadProfileAutoCloseConnection`
6. 如果 `useHotReloadProfile` 为 true：
   - 调 `mihomoHotReloadConfig()`。
   - 如果 `hotReloadProfileAutoCloseConnection` 为 true，再调用 `mihomoCloseAllConnections()`。
7. 如果 `useHotReloadProfile` 为 false：
   - 调 `restartCore()`。
8. 如果上述过程抛错：
   - 回滚 `profile.yaml`，把 `current` 写回旧值。
   - 把错误继续抛给 renderer。

这个“先写 current，失败再回滚”的状态处理比 KumoApp 更强一些。KumoApp 的 current 写入后，如果 restart 失败，文档层面看到的是 current 可能已经持久化；Clash Party 切换失败会主动回滚。

### 运行时配置生成

无论热重载还是重启，Clash Party 都会先走 `generateProfile()` 生成最终配置。

`generateProfile()` 做的事情：

1. 读取最新 `profile.yaml` 的 `current`。
2. 读取 app config：
   - `diffWorkDir`
   - `controlDns`
   - `controlSniff`
   - `useNameserverPolicy`
3. 读取当前 Profile item 和 Profile YAML。
4. 读取当前 Profile 关联的 override：
   - 全局 override
   - Profile 自身 override
   - Smart override
5. 对基础 Profile 依次应用普通 override。
6. 应用规则 override。
7. 应用 Smart override。
8. 读取 `mihomo.yaml` 里的受控 Mihomo 配置。
9. 根据 app 开关过滤受控配置：
   - `controlDns` 关闭时删除 `dns` 和 `hosts`。
   - `controlSniff` 关闭时删除 `sniffer`。
   - `useNameserverPolicy` 关闭时删除 `dns.nameserver-policy`。
10. 用 `deepMerge(currentProfile, controledMihomoConfig)` 合并，受控配置覆盖 Profile。
11. 如果关闭 DNS 控制且最终没有启用 DNS，会清空 `tun.dns-hijack`，避免劫持后无人处理。
12. 对 Smart override 场景补充代理服务器 IP 的 TUN route exclude。
13. 确保 `log-level` 至少是 `info` 或 `debug`。
14. 删除空的 `lan-allowed-ips`。
15. 写出运行时配置：
   - `diffWorkDir == false`：写到 `mihomoWorkConfigPath("work")`。
   - `diffWorkDir == true`：写到当前 Profile 专属工作目录 `mihomoWorkConfigPath(current)`，并复制 geo 数据等资源。

这和 KumoApp 很像：用户 Profile 是输入，App 自己合并 override 和受控 runtime key，最终生成给 mihomo 使用的 config。

### 默认重启路径

默认 `useHotReloadProfile` 为 false，所以切换 Profile 会调用 `restartCore()`。

`restartCore()` 做的事情：

1. 如果已有重启任务在跑，跳过重复请求。
2. 设置 `isRestarting = true`。
3. 调 `stopCore()` 显式停止当前 core。
4. 最多重试 3 次 `startCore(false, true)`。
5. 每次失败后等待一段时间，再 `stopCore()` 和 `cleanupSocketFile()` 后重试。
6. finally 中恢复 `isRestarting = false`。

`stopCore()` 会：

- macOS 上先尝试 `recoverDNS()`。
- 对当前 `child` 发 `SIGINT`。
- 停止 traffic / connections / logs / memory stream。
- 刷新 axios instance。
- 停止 pid file 记录的 core。
- 清理 IPC socket / named pipe。

`startCore()` 会：

1. `prepareCore()`：
   - 确保运行时文件存在。
   - 读取 app config 和 `mihomo.yaml`。
   - 清理轻量模式遗留后台 core。
   - 管理 Smart override。
   - 调 `generateProfile()` 生成配置。
   - 用 mihomo `-t -f <config> -d <testDir>` 校验配置。
   - 如需要，设置 DNS。
   - 生成动态 IPC 路径。
2. `spawnCoreProcess()`：
   - 执行 `mihomo -d <workDir> <ctlParam> <ipcPath>`。
   - macOS/Linux 使用 `-ext-ctl-unix`。
   - Windows 使用 `-ext-ctl-pipe`。
3. 监听 stdout：
   - 等待 RESTful API unix/pipe listening。
   - 等待 provider 初始化。
   - 启动 traffic / connections / logs / memory stream。
   - 上传 runtime config。
   - 再 patch 一次 `log-level`。

所以默认路径明确是 stop/start，不是热 reload。

### 可选热重载路径

如果用户打开 `useHotReloadProfile`，切换 Profile 会调用 `mihomoHotReloadConfig()`。

`mihomoHotReloadConfig()` 做的事情：

1. 调 `generateProfile()` 生成当前 Profile 的最终运行时配置。
2. 根据 `diffWorkDir` 选择 config path：
   - `diffWorkDir == false`：`mihomoWorkConfigPath("work")`
   - `diffWorkDir == true`：`mihomoWorkConfigPath(current)`
3. 通过 IPC/Unix socket 获取 controller axios instance。
4. 调 `PUT /configs?force=true`，body 为 `{ path: configPath }`。

这条路径不关闭 mihomo 进程。它和 ClashX.Meta 的 reload 思路接近，但多了一步：Clash Party 仍然先生成 App 受控的 runtime config，再把生成后的路径交给 mihomo reload。

如果 `hotReloadProfileAutoCloseConnection` 打开，热重载成功后会额外 `DELETE /connections` 关闭所有连接。

### 当前 Profile 内容更新

`setProfileStr(id, content)` 更新某个 Profile 文件时也有类似逻辑：

1. 写入 `profiles/<id>.yaml`。
2. 如果更新的是当前 Profile：
   - 先尝试 `mihomoHotReloadConfig()`。
   - 热重载失败时 fallback 到 `restartCore()`。

这里即使全局 `useHotReloadProfile` 默认关闭，编辑当前 Profile 内容时也优先尝试热重载，失败才重启。

## 对照总结

| 维度 | ClashX.Meta | KumoApp | Clash Party |
| --- | --- | --- | --- |
| 配置单位 | `~/.config/clash/<name>.yaml` | `profiles/<id>.yaml` + metadata | `profile.yaml` 的 `current` + `profiles/<id>.yaml` |
| 当前选择 | `UserDefaults.selectConfigName` | `profiles/current.txt` | `profile.yaml` 的 `current` |
| 切换时是否启动 core | 会先 `startProxy()` 确保 core running | 不运行时只记录选择；运行时才 restart | 默认 restart；热重载开关打开时 reload |
| 是否关闭 mihomo | 不关闭，走配置 reload | 运行中切换会 stop/start | 默认 stop/start；热重载时不关闭 |
| 应用方式 | core/controller reload 指定 YAML 路径 | 重新生成 `work/config.yaml` 后重启 core | 先生成 runtime config；默认重启，或 `PUT /configs?force=true` |
| 受控 runtime key | 主要由当前 YAML / core reload 决定，另恢复 mode | Kumo 移除并重写受控 key，订阅不能覆盖 | `deepMerge(profile, mihomo.yaml)`，受控配置覆盖 Profile |
| 代理组记忆 | 按 config 恢复 `SavedProxyModel` | 当前没有 per-profile 恢复 | 默认 Mihomo `profile.store-selected: true`，由 core 存储选择 |
| mode 恢复 | 切换成功后 replay `selectOutBoundMode` | mode 存在 `state.json`，生成 runtime config 时写入 | mode 来自受控 `mihomo.yaml` 合并结果 |
| 文件监听 | 切换成功后 watch 当前 YAML | 未看到对 profile 文件变化的 watch | 未看到切换后 watch 当前 Profile；编辑当前 Profile 会 reload/fallback restart |
| 系统代理 | 切换配置本身不直接重设系统代理 | 切换 profile 本身不直接重设系统代理，runtime settings 变化时会重套 | 切换 Profile 本身不直接重设系统代理；重启时会处理 DNS/TUN 相关状态 |
| 失败行为 | 不更新当前配置名，不做后续恢复 | `performLoadingTask` 捕获错误并显示；`current.txt` 已写入后若 restart 失败，选择可能已持久化 | 先写新 current；失败后回滚到旧 current 并抛错 |
