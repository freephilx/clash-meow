# 配置解析

本文整理同类开源项目处理 Clash / Mihomo YAML 的方式，并给出 `clash-meow` 最适合采用的配置解析方案。

## 结论

`clash-meow` 已采用“三层解析”方案：

1. **运行时真相交给 mihomo**：最终能否运行、字段语义是否有效，由 mihomo 启动或 `PUT /configs?force=true` 校验决定。
2. **App 写入和合并使用结构化 YAML parser**：Profile 切换、受控 runtime config 生成、TUN/端口/controller 等关键字段写入，使用 Swift `Yams` 解析成结构化对象后再合并和序列化。
3. **UI 预览允许轻量容错解析，但只读且低风险**：概览、配置列表、离线节点预览可以继续使用轻量解析作为短期过渡，但必须容忍复杂 YAML、重复 key、嵌套数组和部分损坏内容，不能让外部订阅导致 App 崩溃。

不建议把用户订阅 YAML 原样作为 App 的运行时真相，也不建议继续扩大手写字符串解析器的职责。手写解析器只适合“展示少量字段”，不适合“修改 YAML、合并 YAML、判断 YAML 语义正确”。

## 开源项目对比

| 项目 | YAML 解析方式 | 应用配置方式 | 对 `clash-meow` 的启发 |
| --- | --- | --- | --- |
| Mihomo / Clash core | core 侧解析完整 YAML，并把结果转换为运行时配置对象。ClashX.Meta 的 Go bridge 会调用 core 的 `config.UnmarshalRawConfig` 和 `executor.ParseWithPath`。参考：[ClashX.Meta goClash/main.go](https://github.com/MetaCubeX/ClashX.Meta/blob/master/ClashX/goClash/main.go)。 | core 启动或 reload 时解析目标配置；失败返回错误。 | App 不应该自己复刻 mihomo 完整语义。最终校验必须交给 mihomo。 |
| ClashX.Meta | Swift UI 不做复杂 YAML 合并；配置切换时把目标 YAML 路径交给 Go core。参考：[ClashX.Meta goClash/main.go](https://github.com/MetaCubeX/ClashX.Meta/blob/master/ClashX/goClash/main.go)、[ConfigManager.swift](https://github.com/MetaCubeX/ClashX.Meta/blob/master/ClashX/General/Managers/ConfigManager.swift)。 | 调用 `clashUpdateConfig(path)`，内部 `executor.ParseWithPath` 后 `executor.ApplyConfig`。 | 简单直接，但 App 对端口、controller、TUN、DNS 等受控字段掌控较弱，不适合作为 `clash-meow` 的长期主路径。 |
| Clash Party / Mihomo Party | 主进程使用 npm `yaml` 包解析和序列化，并对个别订阅兼容问题做预处理，例如 `short-id` 自动加引号。参考：[utils/yaml.ts](https://github.com/mihomo-party-org/clash-party/blob/smart_core/src/main/utils/yaml.ts)。 | 读取 Profile、Override 和受控 `mihomo.yaml`，用 deep merge 生成 runtime config，再重启或 hot reload。参考：[core/factory.ts](https://github.com/mihomo-party-org/clash-party/blob/smart_core/src/main/core/factory.ts)、[utils/merge.ts](https://github.com/mihomo-party-org/clash-party/blob/smart_core/src/main/utils/merge.ts)、[core/mihomoApi.ts](https://github.com/mihomo-party-org/clash-party/blob/smart_core/src/main/core/mihomoApi.ts)。 | 受控 runtime config 是值得借鉴的主线：用户 Profile 是输入，App 受控配置最后覆盖。 |
| KumoApp | Swift 侧直接依赖 `Yams`。节点预览使用结构化解析读取 `proxies` / `proxy-groups`，非法条目跳过。参考：[Package.swift](https://github.com/ProjectKumo/KumoApp/blob/main/Package.swift)、[ProfileNodeParser.swift](https://github.com/ProjectKumo/KumoApp/blob/main/Sources/KumoCoreKit/Configuration/ProfileNodeParser.swift)。 | `RuntimeConfigBuilder` 把 Profile 和 override 解析为结构化对象，移除 App 受控顶层 key，再追加受控 runtime settings。参考：[RuntimeConfigBuilder.swift](https://github.com/ProjectKumo/KumoApp/blob/main/Sources/KumoCoreKit/Configuration/RuntimeConfigBuilder.swift)、[profiles-runtime-configuration.md](https://github.com/ProjectKumo/KumoApp/blob/main/docs/core/profiles-runtime-configuration.md)、[dns-and-sniffer-configuration.md](https://github.com/ProjectKumo/KumoApp/blob/main/docs/core/dns-and-sniffer-configuration.md)。 | 和 `clash-meow` 技术栈最接近。推荐优先借鉴：Swift + Yams + 受控 key 移除 + runtime YAML 重新生成。 |

## 本项目现状

当前 `clash-meow` 主要有三类 YAML 处理：

1. **轻量读取**：
   - `MihomoConfig.parsed(from:)` 读取端口、mode、allow-lan、tun、controller 等少量字段。
   - `ProxyNodeInfo.parsed(from:)` 和 `ProxyGroupItem.parsed(from:)` 为 UI 预览解析节点和节点组。
   - `MihomoConfig.listeningPorts(from:)` 用于启动前释放端口。
2. **结构化写入**：
   - `RuntimeConfigBuilder` 使用 `Yams` 解析 Profile 原文，移除 App 受控顶层 key，再写出 runtime config。
   - `MihomoYAMLSettings.setTunEnabled(...)` 是薄封装，内部通过 `RuntimeConfigBuilder.setTunEnabled(...)` 结构化更新 `tun.enable`。
3. **导入校验**：
   - `ProfileRepository.isLikelyMihomoYAML(...)` 只做兼容性初筛。
   - 远程订阅可能是原始 YAML，也可能是 base64 订阅文本，先通过 `SubscriptionDocumentNormalizer` 归一化。

近期崩溃说明了手写解析的边界：订阅里的代理节点包含 `alpn: - h3` 这类嵌套数组时，如果只按字符串前缀找 `- `，就可能把嵌套数组误当成代理节点；如果再用 `Dictionary(uniqueKeysWithValues:)` 假设节点名唯一，就会被外部配置触发 fatal crash。

因此，当前轻量解析器必须坚持这些底线：

1. 外部 YAML 输入不能触发 `fatalError`、`try!`、`as!` 或唯一 key 崩溃。
2. 只读预览可以跳过非法条目，但不能阻断整个 App。
3. 重复节点名、重复 header 字段采用“后者覆盖前者”的稳定策略。
4. 嵌套数组、嵌套对象不能被误判为顶层 `proxies` 或 `proxy-groups` 条目。
5. 轻量解析结果只能用于展示和提前释放端口，不能作为最终运行语义；端口解析必须只读取顶层监听字段，不能把代理节点里的 `port` 当成本机监听端口。

## 推荐方案

### 近期方案

保持当前轻量解析器，但收紧职责边界：

1. `ProxyNodeInfo.parsed(from:)`、`ProxyGroupItem.parsed(from:)` 只服务 UI 预览。
2. `MihomoConfig.listeningPorts(from:)` 只服务启动前端口释放；解析不到时宁可少释放，也不能误杀无关进程。它只读取顶层 `port`、`socks-port`、`mixed-port`、`redir-port`、`tproxy-port`、`external-controller` 和顶层 `dns.listen`。
3. `MihomoYAMLSettings.setTunEnabled(...)` 已切到结构化 YAML 写入；任何写入后仍必须通过 mihomo reload/restart 和运行时校验确认生效。
4. 所有从订阅、文件、HTTP header 来的数据都要用容错字典构建，禁止 `Dictionary(uniqueKeysWithValues:)` 处理外部输入。
5. 对近期真实失败配置保留回归测试：嵌套 `alpn`、重复节点名、inline map、普通 block map。

### 已采用的中期方案

已引入 `Yams`，并建立 `MihomoYAMLDocument` / `RuntimeConfigBuilder`：

1. `Profile` 原始 YAML 保存在 `profiles/<id>.yaml`，不直接修改。
2. 切换 Profile、冷启动恢复选中 Profile，或修改 TUN/DNS/Sniffer/端口/controller 时，读取 Profile 原文并用 `Yams.load` 解析成结构化 mapping。
3. 当前移除 App 受控或需要重建的顶层 key：
   - `external-controller`
   - `secret`
   - `port`
   - `socks-port`
   - `mixed-port`（先移除旧值，再在 runtime settings 中写入；没有 App 显式端口偏好时继承 Profile 原值）
   - `redir-port`
   - `tproxy-port`
   - `mode`
   - `allow-lan`
   - `log-level`
   - `tun`
   - `dns`
   - `sniffer`
   - 后续 App 明确接管的其他 key
4. 追加 `clash-meow` 受控 runtime settings，生成 `~/.config/clash-meow/config.yaml`。
5. 生成后先运行 mihomo 配置检查或启动/reload 校验。
6. 校验成功后再提交当前 Profile、UI 状态和偏好；失败则不提交或回滚。
7. 冷启动时即使当前 Profile ID 没有变化，也要比较磁盘 runtime 与重新生成结果；不一致时先重写 runtime，再启动 mihomo。

这条路径和 KumoApp、Clash Party 的策略一致：Profile 是输入，runtime config 才是运行时真相。

### 长期方案

把所有 YAML 修改收敛到一个 builder：

1. TUN、DNS、Sniffer、系统代理关联端口、controller、mode 都不再直接改用户 Profile。
2. UI 表单只写 App 自己的设置模型，例如 `settings.json`。
3. `RuntimeConfigBuilder` 每次根据 Profile + App 设置生成 runtime YAML。
4. 复杂 override 后续再加，先支持 YAML override；JavaScript transform 等能力需要额外沙箱设计后再考虑。
5. 文件监听区分两类：
   - Profile 原文变更：重新生成 runtime config。
   - App 生成的 runtime config 变更：只作为内部写入，不触发外部配置切换逻辑。

## 为什么不直接全面手写解析

Mihomo YAML 已经包含大量复杂结构：节点数组、provider、rule-provider、DNS、TUN、Sniffer、hosts、inline map、锚点、merge key、带特殊字符的 key、字符串/数字/布尔混合字段。手写解析容易在这些场景失真：

1. 缩进层级错误：把嵌套数组当顶层数组。
2. 类型错误：把 `"7890"`、`7890`、`true`、`"true"` 混在一起处理。
3. inline map / block map 覆盖不完整。
4. YAML merge key、anchor、alias 无法正确处理。
5. 写回时破坏原结构，导致 mihomo 可读性或语义变化。

所以手写解析只能作为只读、低风险、可降级的 UI 辅助。凡是涉及写回、合并、生成 runtime config，都应该使用结构化 YAML parser。

## 实施顺序

1. 已保留并测试现有轻量解析器的容错行为。
2. 已在 `Package.swift` 和 Xcode 工程中加入 `Yams`。
3. 已新增 `RuntimeConfigBuilder`，把 Profile 激活改为“Profile 原文 + App 受控设置 -> runtime config”。
4. 已把 `MihomoYAMLSettings.setTunEnabled(...)` 替换为结构化写入。
5. 后续继续把 DNS/Sniffer 的 UI 设置和 override 合并能力补进 builder。

每一步都必须有回归测试，并保留真实订阅样本的结构特征测试，避免外部配置再次导致 App 崩溃。
