# 管理员权限

本文记录 Clash Meow 对管理员权限、privileged helper 和 root core 的推荐处理方式，并对比 ClashX.Meta、KumoApp、clash-party 三个开源项目的相关做法。

## 推荐方案

Clash Meow 采用“启动前置校验 privileged helper + 主进程普通权限运行 + helper 执行最小特权操作 + 明确校验和回滚”的策略。

1. App 主进程始终按普通用户权限运行。
2. App 启动时必须校验 `com.clash.meow.helper` 是否已安装且版本匹配。
3. 如果 helper 未安装或需要更新，启动阶段立即请求管理员授权安装。
4. helper 未就绪时，不继续执行配置恢复、core 启动、系统代理、TUN 等主要操作。
5. helper 安装后，后续特权操作通过 XPC 发给 helper，不再反复弹出管理员密码窗口。
6. helper 只暴露白名单接口，不接受任意 shell 命令。
7. helper 操作必须可观测：写入 `app.log`，关键 core 输出继续写入 `core.log`。
8. 每次特权操作完成后，App 侧必须用实际状态校验结果，而不是只相信 helper 调用成功。

## 进程边界

Clash Meow 按 control plane 和 server plane 切分：

1. `com.clash.meow` 负责 UI。
2. `com.clash.meow.helper` 负责 mihomo server。

`com.clash.meow` 的职责：

1. 展示 UI、toast、事件和日志。
2. 管理配置文件、Profile、用户偏好和导入刷新流程。
3. 通过 mihomo controller API 读取运行状态、切换模式、选择节点、热重载配置。
4. 做运行时校验、失败回滚和用户可见错误提示。
5. 向 helper 发起结构化的 server 生命周期请求。

`com.clash.meow.helper` 的职责：

1. 安装后作为 root privileged helper 运行。
2. 负责 mihomo server 的启动、停止、重启。
3. 负责维护 helper 托管的 mihomo PID 和日志输出。
4. 负责 root 权限下的端口释放。
5. 确保同一时间只托管一个 mihomo server，启动或重启前先停止旧 server。

这样划分后，App 主进程不再是 mihomo 的进程 supervisor；它是 UI 和控制器。helper 才是 mihomo server 的 owner。

需要管理员权限的场景：

1. App 启动时安装或更新 privileged helper。
2. 普通权限无法释放被其它用户或 root 进程占用的监听端口。
3. 启动、停止或重启 mihomo。App bundle 环境下 core 生命周期统一由 helper 托管，并以 root 启动 mihomo。

不应请求管理员权限的场景：

1. 端口未被占用。
2. 端口只被当前 App 正在运行的 mihomo 占用。
3. 端口被当前用户可管理的旧进程占用，且普通 `SIGTERM` / `SIGKILL` 可以释放。
4. 只修改 Clash Meow 自己的配置、偏好、日志或 Profile。
5. 系统代理可以通过当前用户权限稳定完成时。
6. TUN 只通过 mihomo API hot reload 成功应用且运行时校验通过时。

## helper 职责

`com.clash.meow.helper` 建议承担这些能力：

1. `version`：返回 helper 版本，用于判断是否需要更新。
2. `releasePorts(ports, excludingPID)`：释放指定监听端口，排除当前 core PID。
3. `startCore(executablePath, configDirectory, configFile, logFile)`：以 root 启动 mihomo。App bundle 环境下所有 core 启动都走这个接口。
4. `restartCore(executablePath, configDirectory, configFile, logFile)`：停止 helper 托管的旧 mihomo 后，以 root 启动新的 mihomo。
5. `stopCore()`：停止 helper 托管的 mihomo。

helper 不应承担这些能力：

1. 不解析和修改用户订阅 Profile。
2. 不决定 UI 开关状态。
3. 不保存用户偏好。
4. 不执行 App 传入的任意 shell 字符串。
5. 不绕过 App 侧的运行时校验。

理由：

1. helper 的边界越小，安全面越小。
2. 配置合成、偏好和回滚逻辑留在 App 主进程，便于测试和解释。
3. helper 只处理必须 root 才能完成的系统操作，符合最小权限原则。

## 授权与安装

安装 helper 使用 macOS `SMJobBless` 流程：

1. App bundle 内带上 helper binary 和 launchd plist。
2. App 的 `Info.plist` 写入 `SMPrivilegedExecutables`。
3. helper 的 embedded `Info.plist` 写入 `SMAuthorizedClients`。
4. App 通过 Authorization Services 获取 `kSMRightBlessPrivilegedHelper` 权限。
5. 调用 `SMJobBless` 安装到 `/Library/PrivilegedHelperTools` 并注册 system launchd job。
6. App 使用 privileged `NSXPCConnection` 连接 helper。

版本策略：

1. App 启动时主动检查 helper。
2. 第一次启动、helper 缺失或 helper 版本不匹配时，立即尝试安装或更新。
3. helper 版本不匹配时先卸载旧 job，再安装新 helper。
4. helper 安装或版本校验成功后，本次 App 会话缓存已验证版本，后续端口释放、core 启停不再重复请求管理员授权。
5. 授权取消或安装失败后，本次 App 会话应短时间暂缓重复请求，避免连续弹窗。

签名策略：

1. 本地开发的 `Sign to Run Locally` / ad-hoc 构建可以使用 identifier-only requirement，降低反复编译时的 cdhash 变化成本。
2. 正式发布必须使用稳定 Developer ID。
3. 正式发布时 `SMPrivilegedExecutables` 和 `SMAuthorizedClients` 应收紧到 app/helper 的 designated requirement。
4. 构建脚本应在签名后校验 app 和 helper 的 requirement 是否互相匹配。

## 端口释放

端口释放按从低权限到高权限的顺序执行：

1. 从当前 runtime YAML 解析监听端口，例如 `mixed-port`、`external-controller`、HTTP/SOCKS/redirect/tproxy 等端口。
2. 查询端口占用进程。
3. 如果没有占用，直接跳过。
4. 如果占用进程是当前 mihomo，排除该 PID，避免 reload/restart 时误杀自己。
5. 如果占用进程属于当前用户，先用普通权限终止。
6. 普通权限释放失败时，再调用 helper 的 `releasePorts`。
7. helper 返回后再次查询端口，确认是否释放成功。
8. 释放失败只影响本次启动或切换，不应永久修改用户偏好。

不推荐把端口释放直接做成“每次启动都弹管理员密码”。端口冲突大多来自旧的当前用户进程，普通权限就能处理；只有 root 或其它用户进程占用时才值得使用 helper。

## core 启动

App bundle 环境下，mihomo 生命周期统一交给 `com.clash.meow.helper` 托管：

1. App 主进程负责 UI、配置生成、controller API、状态校验和回滚。
2. helper 负责 `startCore` / `restartCore` / `stopCore`。
3. `startCore` 和 `restartCore` 每次先停止 helper 托管的旧 core，再以 root 启动新的 mihomo。
4. App 停止内核时调用 `stopCore`，避免 root core 遗留。
5. SwiftPM、单元测试或非 app bundle 调试环境可以保留普通子进程启动路径，避免测试环境触发系统授权。

统一 root 启动的理由：

1. 管理员 helper 已经是 App 启动前置条件，core 生命周期不应再分成普通和特权两条路径。
2. TUN、路由、DNS hijack 等能力都依赖 mihomo 进程权限。
3. 避免先普通用户启动，开启 TUN 时再切换到 root core 的二阶段状态跳变。
4. 端口释放、core 启停和 TUN fallback 都由同一个 privileged supervisor 管理，更容易排障。

## TUN 应用

macOS 上，TUN 的关键权限不是“修改 YAML”，而是 mihomo 进程是否有权限创建 `utun` 并配置系统路由。由于 App bundle 下 mihomo 已统一由 helper 以 root 启动，TUN 应用只需要关注结构化写入 runtime config、配置 reload、运行时校验和失败回滚。

推荐流程：

1. 用户开启增强模式时，先通过 `RuntimeConfigBuilder` / `Yams` 结构化写入受控 runtime YAML 中的 `tun.enable=true`。
2. 优先尝试 `PUT /configs?force=true` hot reload。
3. reload 后调用 `GET /configs` 校验运行时 `tun.enable`。
4. 如果 reload 成功且校验一致，不重启 core，也不请求管理员授权。
5. 如果 reload 失败、超时或运行时校验不一致，fallback 到 restart。
6. fallback restart 通过 helper 重启 root mihomo。
7. root core 启动后等待 controller ready，再读 `GET /configs` 校验 TUN 状态。
8. 校验失败时回滚 runtime YAML、按钮、`tunEnabled` 和 `tunUserEnabled`。

启动恢复时也遵循同样规则：

1. 如果 `preferences.json` 中 `coreEnabled=true`，启动 core。
2. App bundle 下始终走 helper root core。
3. controller ready 后再恢复系统代理和用户意图中的 TUN 状态。

这个策略避免两个问题：

1. 普通用户进程启动 TUN 时出现 `operation not permitted`。
2. 每次用户点 TUN 都无条件弹管理员密码。

## 系统代理

系统代理的权限策略应独立于 TUN：

1. 优先使用当前用户权限设置系统代理。
2. 如果当前系统接口或网络服务需要 helper 才能稳定修改，再把系统代理开关纳入 helper 白名单接口。
3. 系统代理开启后必须验证系统网络设置是否指向当前 mixed-port。
4. 失败时恢复 UI 和 `systemProxyEnabled`，不覆盖 `systemProxyUserEnabled`。

如果未来将系统代理纳入 helper，接口应是结构化参数，例如：

1. `enableSystemProxy(host, port, bypass)`
2. `enablePAC(url)`
3. `disableSystemProxy()`
4. `restoreSystemProxy(snapshot)`

不要传入任意 `networksetup` 命令字符串。

## 失败处理

管理员权限相关失败分为四类：

1. 用户取消授权。
2. helper 安装或更新失败。
3. helper XPC 连接失败或超时。
4. helper 操作执行成功但运行时校验失败。

处理原则：

1. 用户取消授权时，不继续弹窗；提示本次操作需要管理员权限。
2. 安装失败时记录 `SMJobBless` 错误码和描述。
3. XPC 失败时重建连接并最多重试一次。
4. helper 操作成功后仍必须做端口、进程、controller 或系统设置校验。
5. 校验失败按业务回滚，例如 TUN 回滚 YAML 和偏好，系统代理回滚 UI 和实际状态。
6. 不把一次失败尝试写成“下次启动自动开启”的成功偏好。

## 安全边界

helper 是 root 进程，必须按安全边界设计：

1. XPC 接口只允许 App bundle 授权客户端访问。
2. helper 不接受任意命令。
3. helper 只操作 App 明确传入的有限对象，例如端口列表、core 路径、配置路径、日志路径。
4. core 路径应来自 App bundle resource 或已知 mihomo 候选路径，不接受用户随意输入的可执行路径。
5. 配置目录应限制在 Clash Meow 工作目录。
6. 日志路径应限制在 Clash Meow 日志目录。
7. helper 每次启动 core 前先停止自己托管的旧 core，避免多个 root core 竞争端口。
8. App 停止 core 时必须调用 helper 停止 root core，避免遗留后台进程。

当前实现的 helper 启动校验：

1. `executablePath` 只允许 App bundle 内的 `Contents/Resources/mihomo`，或 `/opt/homebrew/bin/mihomo`、`/usr/local/bin/mihomo`、`/usr/bin/mihomo` 这些明确候选路径。
2. `configDirectory` 必须位于 `~/.config/clash-meow/runtime/mihomo` 形态的工作目录。
3. `configFile` 必须是该工作目录下的 `config.yaml`。
4. `logFile` 必须是该工作目录下的 `core.log`。
5. 不满足上述条件时，helper 拒绝启动 mihomo 并把错误返回 App。

### ClashX.Meta

ClashX.Meta 使用 `SMJobBless` 安装 privileged helper，并通过 privileged XPC 调用 helper。它的 helper 能处理 core 启停、端口查询、系统代理、TUN DNS hijack/revert 和 DNS cache flush。

可借鉴点：

1. 使用 `SMJobBless` 和 `NSXPCConnection.Options.privileged`。
2. helper 通过消息类型暴露白名单能力。
3. helper 版本检查、安装、更新和 XPC 连接复用集中在 `PrivilegedHelperManager`。
4. TUN 运行时变化后同步 helper 处理 DNS hijack/revert。

不完全照搬点：

1. ClashX.Meta 的部分 TUN 更新失败只记录日志，Clash Meow 应把失败返回 UI 并回滚状态。
2. Clash Meow 应更严格地区分用户意图和最后一次成功应用的实际状态。

### KumoApp

KumoApp 把 TUN 权限明确表达为“需要 Kumo Helper 或 privileged process”。当 helper service 可用时，core start/stop/restart 和 TUN 操作走 service；不可用时，TUN 状态会标记 `requiresService` 并抛出错误。

可借鉴点：

1. UI 明确展示 helper 状态。
2. TUN 权限不是 VPN 配置弹窗，而是 core 进程权限问题。
3. service backend 和普通 in-app supervisor 的职责分开。
4. 无权限时返回明确错误，不假装开启成功。

不完全照搬点：

1. KumoApp 更偏 service-first/restart-only；Clash Meow 可以保留 mihomo `PUT /configs?force=true` hot reload 作为优先路径。
2. Clash Meow 采用 KumoApp 的 supervisor 边界，把 App bundle 下所有 mihomo 生命周期交给 helper；但 TUN 配置应用仍优先使用 mihomo hot reload，失败后才重启 root core。

### clash-party

clash-party 在 macOS 上通过 `party.mihomo.helper` 处理系统代理，helper 不可用时会尝试启动服务或重建 socket。TUN 权限路径则会对 core 执行 `chown root:admin` 和 `chmod +sx`，让 mihomo 可执行文件具备提权能力。

可借鉴点：

1. helper 请求失败时检查 helper 是否运行、socket 是否存在，并做有限重试。
2. 系统代理走 helper，非 macOS 平台走普通平台能力。
3. TUN 权限在启动时校验；无权限时不静默假装成功。

不推荐照搬点：

1. 不建议对 App bundle 内的 mihomo 执行 setuid。
2. setuid core 难以和签名、更新、回滚、安全审计保持一致。
3. Clash Meow 更适合让 root helper 作为 supervisor 启动 mihomo，而不是把 mihomo binary 本身改成 setuid。

1. [clash-party/src/main/sys/sysproxy.ts](https://github.com/mihomo-party-org/clash-party/blob/7ea11bb6452ea05a1d2b2eead0b7f001f05baef4/src/main/sys/sysproxy.ts)

## Clash Meow 的最终取舍

Clash Meow 选择 `com.clash.meow` 负责 UI、`com.clash.meow.helper` 负责 mihomo server，理由如下：

1. **权限边界清楚**：UI 进程不需要 root；root 进程只做 server 生命周期和必要系统操作。
2. **状态来源清楚**：App 通过 controller API 和 helper 返回值观察 server，不再同时扮演 UI 和进程 supervisor。
3. **减少启动路径分叉**：不再根据 `tun.enable` 决定普通启动还是 root 启动，避免开启 TUN 时从普通 core 切到 root core。
4. **更容易排障**：helper 管 start/stop/restart，App 管配置和校验；日志中可以明确看到问题在 UI/control plane、helper/supervisor，还是 mihomo runtime。
5. **比 setuid 更可控**：helper 受 `SMJobBless`、`SMPrivilegedExecutables`、`SMAuthorizedClients` 约束；不修改 mihomo binary 权限，更新和签名更稳定。
6. **保留 mihomo 能力**：TUN 配置仍优先走 `PUT /configs?force=true`，不因为 helper 托管 core 就把所有设置都变成重启。

推荐落地为以下规则：

1. helper 是 App 启动必需条件，启动时必须安装或更新到匹配版本。
2. helper 未就绪时停止后续启动恢复，只提示用户完成管理员授权。
3. 端口释放先普通权限，失败再 helper。
4. App bundle 下所有 mihomo start/stop/restart 都通过 helper 托管。
5. TUN 优先 hot reload，失败时通过 helper 重启 root core。
6. 系统代理暂时维持普通权限实现；未来如纳入 helper，必须使用结构化白名单接口。
7. helper 安装失败会阻止主要功能继续运行，但不应破坏已有配置和偏好。
8. 所有需要管理员权限的功能都要有运行时校验和回滚。
9. 开发签名可以放宽 requirement；正式发布必须收紧到 designated requirement。
